# Architecture: the interface for AI

Part of [architecture.md](../architecture.md), the design as implemented. The MCP server, its tools and the bridge to the running app.

## Rozhraní pro AI (D33)

```
klient AI ──stdio──▶ MCP server (Node) ──┬─▶ vlastní engine (dokument ze souboru)
                                         └─▶ most HTTP 127.0.0.1 ──▶ engine běžící aplikace
```

**Nástroje** jsou čisté funkce nad `Engine` (`tools.ts`), takže tentýž kód obsluhuje engine v serveru i engine aplikace. Server k nim přidává nástroje pro soubory, které potřebují disk.

| Nástroj | Co dělá |
|---|---|
| `describe_api` | Konvence, katalog vazeb s operandy a příklady, typy dokumentu a příkazů. Generuje se ze zdrojů enginu. |
| `get_model` | Časová osa se stavy a chybami, tělesa s objemem a rozměry; `at` = stav po dané feature. An extrusion with a generated profile carries its `facts`. Every body carries what its body properties state beyond the defaults (D48): `name` when it has one of its own, `color`, `material`, `use` when it is not `part`, `density`, `mass` in g with `massFrom`, and `from`, the body a copy takes after. The answer has `bodyPropertyErrors` (body, field, message: a density or a mass that cannot be evaluated, own or inherited) and, without `at`, `bodyPropertiesWithoutBody` (entries whose body is gone). With a stored mesh, `meshes`: ID, name, triangles, the size of the bounds and `usedBy`, the features that place it (D55). |
| `get_document` | Dokument tak, jak se ukládá, nebo jedna feature. A stored mesh (D55) is shown without its two texts of base64: its name and how many characters they have (`save_document` writes them). A stored document (D62) is shown shortened: its name, its parameters, the number of its features and of its own stored documents, and how many characters the rest has; `stored: "<id>"` (or a path `kit/bearing` into stored documents of stored documents) prints that document whole, or one of its features with `feature`. |
| `get_sketch` | Body s polohami, křivky, vazby, promítnutá geometrie, oblasti, diagnostika a slovní rada (`advice`). A constraint with expressions lists them by value name (`expressions: { value: "module * Zs" }`), so a constraint with more than one value stays unambiguous. |
| `get_parameters` | Parameters with expressions, values and errors; checks with their result. |
| `explain_constraint` | Jestli vazba plyne z ostatních a ze kterých. |
| `get_body` | Stěny (rovinnost, plocha, normála) a hrany (druh, délka; u přímé krajní body, u kruhové střed a poloměr) se jmény použitelnými v odkazech. The volume, the bounds, the faces and the edges are those of the query `body`, in the pose of the document, with the note about the pose beside them (D49). |
| `check_interference` | Colliding pairs of bodies with the shared volume, fits, pairs the kernel refused and its intersection as computed cleared (`cleared`, D50, rounded like the others), and pairs neither colliding nor clear (`failed`, with what was measured when the kernel refused them); `bodies`, `threshold`, `at`. In the pose of the document, with the note about the pose beside the answer; a body whose pose is not known is an error of the call with the reason (D49). |
| `query` | Asks any query of the catalog of the engine: `query` (its name), `args`, `at` (the state after a feature) and `after` (a command previewed first; the query is asked about the result and nothing is written; with both, the document after the command is evaluated up to `at`). Numbers of the answer are rounded to six decimal places, and the keys a query lists in `significant` to that many significant digits. An error is a text that starts with its code. The queries with their arguments are in `describe_api`, section Queries (D37). With a mechanism (D49) the answer is in the pose of the state asked about, with the note about the pose beside it; `geometry: "modelled"` asks about the model as modelled. |
| `execute`, `preview` | Příkaz enginu (i `batch`); `preview` nezapisuje. Výsledek shrne, co není v pořádku, a u každé skici řekne, jestli je vyřešená a kolik má volnosti. It also reports what is not a feature state: `bodyPropertyErrors` and `bodyPropertiesWithoutBody` (D48), `failedChecks`, `parameterErrors`, and `fieldErrors` of features. |
| `sketch_tool` | Runs a sketch tool of the engine (`sketchTool`) in a sketch: `{ sketch, tool, input, prefix?, preview? }`. It generates the IDs with `freshIds` (optionally with a prefix), writes the batch as one command (or only computes it with `preview: true`) and returns `ids` with what `execute` returns. |
| `undo`, `redo` | Historie příkazů. |
| `session_status` | Jestli nástroje pracují nad aplikací, nebo nad vlastním dokumentem serveru. |
| `export` | Exports the model in a format of the catalog `EXPORT_FORMATS`: `format`, `path`, `options` (of the format, checked by the engine), `overwrite`, and `at` and `after` as for `query`. The engine (of the server or of the app) answers the hidden tool `_export` with the files as base64 (`ToolAnswer` of the kind `files`), and the server writes them with the writer of `export_stl` (`export-writer.ts`): a `file` layout to `path`, which is overwritten; a `directory` layout into the folder `path` with the same guarantees as `export_stl` per body. An export with nothing in it is refused with the text of the format. The formats are `stl`, `3mf` (the bodies as named objects of one 3MF package, D54; its items deflated by the compressor both engines are given, `packages/deflate-pako`, so the file crosses the bridge about a sixth of its stored size), and `dxf` and `svg` (the outline a plane cuts out of bodies, D54); the answer lists every written file with its `about` (for an outline the bodies cut, the loops and circles, the area, the box, the frame and how far under it the cut was taken). The server needs no code for a format: the tool takes its name from the catalog and `describe_api` describes it in its section *Export formats*. In `options`, and in `args` of the tool `query`, a `null` at the top level counts as not given, as for the arguments of every tool. The writer knows only files directly in the folder: a path with a folder is refused until the first format that has one adds the folders to the writer. |
| `insert_document` | Stores a document file as a part (D62): `path`, `id`, `name`, `replace`. The server reads the JSON and sends `addDocument` (the ID by default from the stem of the file, `idFromFile` with `document` as the fallback, numbered when taken; the name the file name) or, with `replace` and `id`, `replaceDocument` (keeps the name). The answer: the ID, the file, `replaced`, the parameters of the document with their values, the bodies an insertion would bring with their use, material and mass (through a preview over the hidden tool `_insertion`, so through the bridge too), a `warning` when the document has features in error, and `next`: the `addFeature` of an insertion on XY under a free feature ID, with what it means in `say` (nothing is inserted yet; the bodies that come in as printed parts). A file that cannot be read, is no JSON or does not load is an error of the call. |
| `import_outline` | Reads a 2D outline (D72): `path`, `format` (by default from the extension, `outlineFormatOf`), `options` of the format (`layers`, `unit`, `weld`), and to place it `sketch`, `id`, `name`, `x`, `y`, `turn`, `anchor`, `regions`; `replace` with `id` reads a revised file into the entry, `remove` lists constraints to remove in the same step. The server refuses a file over 8 million bytes by its size, reads it and hands the bytes as base64 to the hidden tool `_outline` where the engine is (its own, or the app's over the bridge, as `_load` carries a document): `outlineInto` is `prepareOutline` (the format, the options: those given whole, or for a replacement of the same format those the entry stores in `readWith`; `importOutline`; the command `addExternal`, or `updateExternal` with the constraints of `remove` before it in one batch) and `execute` of that command. Without `sketch` the answer is the report alone. A command the engine refuses comes back in an answer that is ok, with `refused` and the report, so nothing changed and the message names the constraints. The answer: `file`, `report`, `entry`, `revision`, `hold` (of a replacement, the constraints that name an entity the new curves take away or change in kind, each with those entities: the engine's `updateHolds`), `refused`, `sketch` (the brief of the sketch after the command), `problems`, `next` in words (after a placement it names the first curve the file gave; after a refusal it advises `remove` only for a replacement that `hold` stops, with the list to send); never the curves. An app older than the server, which has no `_outline`, is told to be reloaded, as for `_export`. `get_sketch` gives the row of an outline a `box` of its curves at their places (`placedOutlineBox`: an arc by the extremes of its circle within its sweep, a spline by its curve), and its `more` starts at the `next` of `entryCurves`. `_outline` is in `MUTATING`: `changesDocument` answers false for a look, a file that cannot be read and a command the engine would refuse (prepared and previewed), so they do not end a draft of the user; `outlineBytes` refuses a text longer than the base64 of the largest file before it decodes anything. The app's status line reads the answer (`outlineSaid`): nothing for a look, the entry and the sketch for a placement, the refusal as an error; a call that fails says nothing for a look and "AI: the outline was not imported: …" for a placement (the bridge client hands `onCall` the arguments of the call). |
| `import_mesh` | Reads a mesh file into a stored mesh (D55): `path`, `format` (by default from the extension, `importFormatOf`), `options` of the format, `id`, `name`. The server reads the file and calls `importMesh`, so what crosses the bridge is the welded mesh; on success it sends `addMesh` through `execute` to the engine the other tools use (the app's when connected). The name defaults to the name of the file trimmed and cut to 200 characters (`meshNameOf`), the ID to its stem reduced to letters, digits and underscores (`idFromFile` of the engine: `mesh` when that is no ID, `_2`, `_3` when taken, against the stored meshes of `get_document`). The answer: the ID, the file, the report (rounded to six decimal places) and `next`, the batch that places the mesh, written out (an `addFeature` of a mesh feature on XY named by the stem of the file, under the ID of the mesh or, when the document uses it for anything — a feature, an entity of a sketch, an ID a section names — the next free one, and `setBodyProperties` with `use: 'reference'`), with the advice to add the mass of the data sheet. A refusal is an error of the call with the code of the import. |
| `open_document`, `save_document`, `export_stl` | Soubory na disku; dokument může být v aplikaci. `export_stl` takes a list of bodies (the printed ones by default: the use `part` of the body properties, D48; a listed reference or auxiliary body is written) and with `perBody` writes one file per body into a directory, named by `bodyFileName`. Per body it writes nothing when a file already exists (unless `overwrite`) or when two names differ only in the case of letters: the names come from IDs, so the caller did not choose them one by one. The files are written into a directory of the call inside the target (`mkdtemp`) under their final names and moved once all are on disk, so a failure while writing leaves the target as it was (directories the export had to create are removed again; the path has to leave room for the 23 characters of that directory; a directory of the call that cannot be removed is named in the answer); if a move fails after others succeeded, the new files that replaced nothing are removed again and the files that replaced old ones are named in the error. Exports run one after another, and a call the tools refuse (an unknown argument) does not reach the app over the bridge. |

Chyba volání (neznámá skica, špatný argument, neplatný příkaz) se vrací jako text s příznakem chyby, ne jako výjimka protokolu. Malý výsledek se vypisuje s odsazením, velký úsporně.

`describe_api` lists the profile generators from `GENERATORS` (operands, parameters with ranges and defaults, references, side names, facts and an example profile). It also lists the expression syntax (operators, functions, constants) and the numeric fields that accept an expression; both come from the engine (`EXPRESSION_FUNCTIONS`, `FEATURE_TYPE_INFO[type].fields`, `CONSTRAINTS[type].values`), so a new field or function shows up without touching the server.

**Mirror and pattern in a sketch (D68).** `describe_api` has a section *Entries of a sketch* generated from `REFERENCE_KINDS` (`entryKinds` of `api.ts`): per kind its `type`, whether it is reference geometry (computed before the solver, may be constrained to) or derived geometry (after it, may not), its `summary`, the numeric fields of its example with their ranges (`fieldsOf` of a sketch that holds the example) and the example (`KindBase.example`, an entry over the fixture the section names: the box `box` from `b1`..`b4` of `base`, the sketch `top` on its top face with `l1`..`l4` and the construction line `cl`); `packages/mcp/test/sketch-pattern.test.ts` builds the fixture and runs every example, and a kind without them does not compile. The hand-written sentence for the edge went. A paragraph of the conventions says to constrain the sources, how a count follows a parameter and what a feature over copies names, that a projection or a copy is no source, and how a mirrored outline closes. **`get_sketch`** lists a derived entry short: its input form (an expression in its field), `source: 'derived'`, `copies` (the copy numbers the last recompute made, as ranges), `step` (a mirror: `axis`, its two points; a row: `shift` of copy 1, and `second` of copy 1000 for a grid, each from the transform when that copy is not made (a first count of 1); a circle: `center` and `angle` of one step) and `first` (the entities of the first copy made: a curve with its kind, a point with its position); the round trip into `updateExternal` changes nothing. Its regions group the equal regions of copies of one derived entry (by the source of its kind) (the outer loop up to the copy number, the area as written, the number of holes) into one row with the reference of the first and `copies: { entry, numbers }`; a copy that differs has its own row. The open ends of copies are a line of `advice` (the count, the entries the listed ends belong to, the first end, its distance and the cure by the transform of its entry: for a mirror a constraint on the axis, for a ring a count or an angle, for a row a spacing, a length or a count, or an open row left as it is; for `twoVertices` the two points to join). The ends of an entry that is not derived (a projection that forms regions, with 6b and 6f) are named as its own ("ends of `e1`", not "of copies of"), with the cure to end an own curve at it or to project the edge that continues it. A row of 200 slots answers in under 1,500 characters.

**An imported outline (D72).** `describe_api` shows `SketchOutline`, `ImportedCurve` and `OutlineReadWith` from `types.ts`, the kind `outline` in *Entries of a sketch* by its summary and example, a generated section *Outline formats* from `OUTLINE_FORMATS` (per format its summary and options, with the limits), and in the paragraph on reference geometry how an outline is placed and how its entities are named. `get_sketch` gives an outline its own row (`outlineDetail`): the input fields with their expressions and `readWith` without the curves, `source: 'reference'`, the counts by kind, the box as placed, the first curves at their places through the query `entryCurves` (at most `OUTLINE_LIMITS.listed` curves holding at most `listedPoints` positions, a spline without `through`), `listed`, `total` and `more` naming the query for the rest. The rows of `regions` are capped (`SKETCH_SHOWN`): at most 50 rows and `regionsNotListed` with the count of the rest; an outer loop of more than 20 IDs is printed as its count, its first 20 IDs, the entries they are under, its `index` among the regions of the sketch and the call of the query `sketchRegions` that gives it whole, so a region of any length is extruded from the answers of MCP alone. `get_document` prints `OUTLINE_OMITTED` in the place of the curves of an outline of more than 50 curves on each of its paths (the whole document, one feature, a stored document; `featureShown`); `save_document` writes them. The advice of an open end of an outline is `OUTLINE_OPEN_END` (a larger `weld`, or an own curve at the end).

**Splines (D70).** `describe_api` shows the curve `{ type: 'spline'; points: Id[] }` and its comment from `types.ts` (what a control point does to the curve, closing by the first point again, the degree and the knots, that the solver sees only the points, tangency at an end by the end leg of the control polygon and the side the solver keeps, that a spline is not cut or projected, the swept side face and the rim that takes no chamfer, the refusals of the offset, the taper, the revolve and the wall, and the change of control points by a batch), with no change in `packages/mcp`. **`get_sketch`** lists an own spline with `points` and, at the positions `at` of its control points shows (the solved ones, else the document's, so an unsolved sketch has them too) and rounded as positions are, `through` (`splineThrough`: the points the curve passes from its start to its end, the joints of its Bezier pieces and the middle of each: five for the grip of scenario 15) and `box` (`splineBox`, `[minX, minY, maxX, maxY]` of the curve itself, half as deep as the box of the control points for the grip); both are left out while a control point has no position, and a copy of 6c, listed short with its entry, has neither. Why a profile with a spline is invalid is the query `sketchContacts`, not a sentence of `advice`: a contact of a spline with another curve (`crossing` or `end`, `fix: 'none'`, the reason that a spline is not cut and holds no point), a spline that crosses itself (one contact whose curves are the spline twice), a spline along a line (`lying`), a spline of no length (`degenerate`), and two ends at one place with `fix: 'join'`. There is no sketch tool for a spline: `addPoint` for each control point and one `addCurve`.

**The axes of the origin (D71).** A paragraph of the conventions says that every sketch has the lines `origin/x` and `origin/y`, which constraints (but `midpoint` and `equalLength`) and an axis `sketchLine` may name and a sketch tool snaps to, and that `get_sketch` does not list them; the comments of `ExternalRef`, of the constraints, of `AxisRef` and of `SketchResult` in `types.ts` say the same where the types are.

`describe_api` has a section *Sketch tools* generated from `SKETCH_TOOLS`: every tool with its inputs (kind, range, optional), the lists of IDs it returns and an example of input, which a test runs through `sketch_tool`. Two input kinds came with trim, extend and split (D65): `curve` (the ID of a curve of the sketch; with `reference`, also of reference geometry, such as a projected edge or an axis of the origin) and `place` (`[x, y]`, nothing made or snapped there). The section says in two sentences that a profile with crossing curves is repaired by `split` without a curve and then `trim` of the pieces that should go, each by a place on it, and that the query `sketchContacts` says where the curves meet and what cannot be cut; the summary of `trim` says when to pass `repair` (`on` wherever a feature reads regions of the sketch or will, `off` only where T shapes are meant). The examples of the three tools run after a rectangle and a line across it. D69 adds two input kinds, `sketch` ("the ID of an earlier sketch of the document") and `entities` ("IDs of points and curves of the sketch `sketch`, as its get_sketch or the query sketchSources lists them"), and the tool `projectSketch`, whose example runs into a sketch after a sketch `base` holding the rectangle of the example of `rectangle`; what it leaves out is one list of `ids` per reason (`skipped`, `doubled`), described in the catalog. `sketch_tool` hands the tool `evaluation.features`. The general part of `describe_api` has a paragraph on projected geometry (D69) for what the reference kinds share: fixed, following the source, frozen when it is gone, constrained with an own operand, the flag `regions` and the joins at the ends, never cut, the outline to cut drawn by `projectSketch` with `as: "own"` (the hold by hand: own points coincident with the projected ends, an own arc held by a construction line from its centre to its start with the projected centre on it, not `equalRadius`), and the ways in (the query `sketchSources`, `addExternal` of the kind `sketch`). `get_sketch` lists a projection's entry with its fields and entities as for any entry (no change), and `openEnds` when ends of flagged projections stayed open (6c's advice says "ends of `e1`").

**Proč se nové vazby a příkazy objeví samy.** `execute` bere jakoukoli hodnotu typu `Command` a validuje ji engine. `describe_api` skládá text ze tří zdrojů: z ručně psaných konvencí, z katalogu vazeb (`CONSTRAINTS`: jméno, shrnutí, operandy a jejich druhy, pravidlo hodnoty) a ze zdrojového textu `engine/src/types.ts` bez sekce portů. Vazba přidaná do enginu je tedy v popisu i v nástrojích bez změny v `packages/mcp`.

**Most.** Server otevře HTTP na `127.0.0.1` (výchozí port 4517). Aplikace se po zapnutí propojení připojí na `GET /events` (proud událostí) a na každý požadavek odpoví `POST /reply`. Dokud je připojená, nástroje se provádějí nad jejím enginem; po odpojení nad vlastním enginem serveru. Platí poslední připojená aplikace; požadavek bez odpovědi do 30 s skončí chybou. Aplikace, kterou jiná vytlačila, dostane událost `displaced` a sama se znovu nepřipojuje (propojení se v ní vypne a jde zapnout zase jen tlačítkem); po výpadku serveru se naopak připojuje sama. Připojit se smí jen stránka z tohoto počítače: server ověřuje původ (`Origin`), cílovou adresu (`Host`) a vlastní hlavičku `x-trymesh-bridge`, kterou musí mít každý požadavek kromě `GET /status`.

**Soubory.** Server si pamatuje soubor vlastního dokumentu a zvlášť soubor dokumentu v aplikaci. Ten platí jen po dobu jednoho připojení a jen pro dokument, který v aplikaci byl, když se do souboru ukládalo nebo z něj načítalo: aplikace s každou odpovědí posílá pořadové číslo dokumentu, které zvýší při každé jeho výměně (Nový, Otevřít, načtení od AI). `save_document` bez cesty ukládá do souboru toho dokumentu, se kterým se právě pracuje; nemá-li žádný, je to chyba. Nástroj složený z více kroků pracuje celý nad enginem zjištěným na svém začátku.

**Spuštění.** `pnpm mcp:build`, pak v klientu AI příkaz `node packages/mcp/dist/server.js` (volby `--file model.json`, `--port`, `--no-bridge`). Pro Claude Code je v kořeni repa `.mcp.json`. V aplikaci se propojení zapíná tlačítkem AI na liště.

**What a tool may answer (D37).** A result of a tool goes through JSON (`callTool`, the bridge), so bytes do not survive it. `ToolAnswer` (`tools.ts`) is the envelope for what is not plain data: `data`, `files` (a layout and files as base64, written by the server: the tool `export`) and `image` (returned to the client as image content of the protocol; its optional `about` says what pixels do not, and the server returns it as a text next to the image). A tool or an operation says by its definition that it answers with one; the server does not guess from the shape of a result.

**Operations of the app (D37).** Something only a running app can do, such as a picture of the viewport, is not a query: the engine has no renderer and the operation is asynchronous. It is an entry of `HOST_OPERATIONS` (`host.ts`, shared by the server and the app): a title, a summary, what it returns, its arguments described like those of a query, and `run(host, args, state, path)` that answers with a promise of `QueryOutcome<ToolAnswer>` (`state`: the state the call asks about; `path`: its `at` and `after` as given, 5b). The registry has one operation, `view_image` (below). A package adds an entry, a line in the map `HostOperations` and what the operation needs of the app as a member of `AppHost`; both interfaces grow by declaration merging, and the app (`connectBridge(engine, { host })`) does not compile until it supplies the new member. The host is the app's own object with its engine (`AppHost & { engine }`); an operation gets it as it is, not a copy, so it may be an instance of a class.

- The server lists every operation as a tool of its own under its key, with a schema generated from the description of its arguments, and `describe_api` has the section *Operations of the app*. (A tool per operation, unlike the queries, because one is planned; if they multiply they get one general tool.)
- **`at` and `after` on the path of every operation** (5b, D59), as the tool `query` takes them beside its `args`; they are not arguments of an operation's description (`hostOperationProblems` refuses an operation with an argument of either name). `hostOperations` of `api.ts` lists them after the arguments of every operation (`OPERATION_STATE_ARGS`), so the input schema of every operation tool (`at` typed a string, `after` an object, as the tool `query` declares them) and `describe_api` have them.
- Without a connected app the tool answers `notAvailable`: the server's own engine has no host. With one, the call crosses the bridge under the name of the operation (the bridge passes the arguments as they are), and the bridge client runs `callHostOperation` next to `callTool`: it takes `at` and `after` out of the arguments and asks the state: with `after` `engine.preview(after, at)` (the preview answers for `at` too, and `after` may add the feature `at` names; a command that does not apply is the answer `after: <code>: <message>`), without it `engine.getState(at)` (an `at` that names no feature of the document is `notAvailable: <operation>: at: …` before the engine is asked; an `at` that is not a text and an `after` that is not an object are `invalidArguments`). Nothing is written. The other arguments are checked with the checker of queries in that state (so a body that only a previewed command adds can be named), the defaults are filled in, the operation runs on that state, and a refusal comes back as `code: operation: message`. `Tool.run`, `callTool` and `connectBridge(engine, …)` stay synchronous and carry only the engine.
- A call is looked up among the operations first, so an operation must not have the name of a tool or a leading underscore (`hostOperationProblems`); the server and `connectBridge` refuse to start with a set that breaks it.

**A picture of the model (`view_image`, `view-image.ts`, D43).** The AI does not see the model; this gives it a picture to check a shape by eye. It is an operation of the app, so it needs the app connected: a picture is drawn by the view of the app, and the server has no renderer.

- *The arguments*: `view` (`iso` as the app starts, `front`, `back`, `left`, `right`, `top`, `bottom`, or `current`, the camera of the user), `bodies` (only these are drawn and the picture is fitted to them: leave out the housing to see the gears), `section` (a plane, an offset and a flip, the three descriptions of the query `section` themselves), `width` and `height` (800 by 600; 64 to 1600 each). The state is that of the path (`at` and `after`, 5b; before 5b `at` was an argument of its own): `after: { type: "setPose", values: … }` draws a pose that is not written. `imageRequest(host, args, state, budget?, after?)` builds the request of that state.
- *What the app gives to it* is one member of `AppHost`, `view`, with one function: a picture of a given state, bodies, camera, cut and size (`ViewCapability.image`). The operation turns its arguments into that request. The cut is the answer of the query `section`, asked with polylines in the same state and of the same bodies: the frame of the plane the section was taken at (`takenAt`) and, per region, its body and its loops. So a picture of a cut model and the section view of the app are drawn from one answer, and a plane that is not there or not planar is answered by the query. A cut is taken only from a complete answer (`completeRegions`).
- *The picture* is of the model, not of the user's screen: the bodies with their edges, each body in its own colour from a fixed palette in the order of the bodies of the state, a cut filled with a darker shade of the colour of its body. No selection, sketches, planes or dimensions. It is drawn off the screen at the size asked for, with a camera and a light of its own, so the same call gives the same picture wherever the user looks (but for `current`) and the user's view does not change.
- *The answer* is the PNG as image content and, as text, `about`: the size, the scale in millimetres per pixel, and the colour of every body of which something is drawn as `#rrggbb` and as a word, with the colour of its cut when the section goes through it. With a section it also lists the bodies the plane goes through (`section.cut`) and the bodies it removes whole (`section.cutAway`), so a picture with nothing in it says why. In a pose (5b) `about.pose` names the joints that move the model with their values (`poseNote` of the drawn state, as the tools `query` and `get_body` put it), and `about.blocked` each joint without a motion with the drawn bodies beyond it: those are drawn with the joint standing at zero (the transform of the link), as the view of the app draws them, and not refused. With a section such a body is refused (`failed` at `section`): the section is a query, posed, and a cut from another pose would be wrong. The text is the operation's own: the joints that block with their faults, the section of the other bodies (`bodies: [...]`), and the joints at zero (`after: setPose`, in one `batch` after the caller's own `after`) only where each can stand there (its only fault is its axis and its limits allow zero, as `blockedText` of a query offers it). A picture whose base64 text is over two million characters is `failed`.
- *Checks.* The arguments are checked in the state asked about by `callHostOperation`; the operation looks the bodies up again in the state it draws (for a caller of `imageRequest` that hands a state of its own). A refusal names its argument in its text as the check does (`bodies[1]`, `section.plane`). `view: current` takes only the camera of the user: nothing is fitted, and the bodies hidden in the app and a section shown there do not count.
- An operation has to answer within the 30 s the bridge waits for any call.
- An exception while the app serves a call is reported by what the call was: a tool that changes the document keeps the warning that the change may have been made; a question (a query, a read, an operation) says that the app failed to answer and that nothing was changed.
- Guards (`packages/mcp/test/host-operations.test.ts`): two tables typed by the map of operations, the rule that the name of an operation is not the name of a tool, and the whole way of a call with operations made up for the test (the server and `connectBridge` take the set of operations as an option).

**Coverage of the engine (D36).** `packages/mcp/test/coverage.test.ts` holds a table typed over the methods of `Engine` that names the tools reaching each one. A new method without an entry does not compile; the test calls each named tool through the server and checks that the engine method ran. Commands need no such table: `execute` takes any `Command` and the description is generated from the engine.

**Body properties (D48).** `execute` adds `takenOver` to its answer: the IDs of the features and sketch entities the command added while a section of the document named them before the command (`takenOver` of the engine). A body made under such an ID takes over the properties of the removed one (a reference part with the mass of a motor); a sketch point or curve only shares the ID, and the answer does not claim more. `describe_api` has a generated section *Sections of the document* from `SECTION_INFO` (what a section holds, its commands, its numeric fields as `<body>/density`), the numeric fields of the sections in *Numeric fields*, the catalog `materials` in *Catalogs*, and a paragraph of the conventions: the three uses, the catalog fills the density (no density from memory), a bought part has its `mass`, a copy takes after its source. The mass query reads the properties (`massSourceOf`), so its answer tells per body where the mass came from (`from`) and lists an auxiliary body in `skipped`.

**The mechanism (D49).** The five commands go through `execute`, `preview` and `after` like any other; the section, its commands and the numeric fields of a joint (with the type each belongs to) are in the generated part *Sections of the document*; the query `mechanism` is reached by `query`. By hand:

- `get_model` has `mechanism` when there is a link: the links with their bodies, the joints with type, parent, child, axis, the numbers (rounded to six decimal places, inside the tolerance of the limits, so a limit read here is accepted as a value) and the expressions, `status: 'error'` for a joint in error (without `at` only, like `jointErrors`), the roots when there are several. Its bodies stay as modelled. The drive of a joint (5b) is listed with its numbers as stored. Without `at` it (and `execute`, `preview`) lists `jointErrors`, `jointDriveErrors` (5b: `{ joint, field, message }` of a drive field whose expression fails; not a fault of the joint, but the export of a robot refuses it), `linksMissingBodies` and `bodiesInNoLink`; with `at` they are left out, as they would name every joint whose sketch comes later and every body not made yet.
- **The note about the pose.** When a joint of the state asked about moves the model and the answer was computed from the bodies in the pose, the tools `query`, `check_interference` and `get_body` return the joints that move it (not one in error or beyond one) beside their result: `about: { pose: { <joint>: value } }` of `ToolOutcome` (a tool returns `Noted`; `callTool` puts the note apart from the result), which the server prints as a second text. The result itself keeps its shape; a document without a pose, a query asked with `geometry: 'modelled'`, the print query and a query that reads no geometry of bodies (`geometry: 'none'` of its entry: `catalog`, `hardwareHole`, the two of a sketch, `mechanism`) answer with one text as before.
- `query` takes `geometry: 'modelled'` (the model as modelled, whatever the pose). `get_body` prints the volume and the bounds of the description of the query `body`, so its answer is all in the pose. `check_interference` catches the failure of a body whose pose is not known (`QueryFailure` out of `Engine.interference`) and answers with its reason as an error of the call; `get_body` turns the failed outcome of the query into one already.
- `execute` lists in `takenOver` also a sketch or a point that became the axis of a joint again and a feature whose body entered a link again (the IDs the mechanism names).
- A paragraph of the conventions in `describe_api`: the zero of every joint is the model as modelled; the sign of a turn; a pose is stepped with `after: setPose`; queries answer in the pose, also with `at`, and fail for a body beyond a joint without a motion, which is read with the joint previewed at zero or with `geometry: "modelled"`; an axis, a sketch point or a plane given to a query is as modelled; exports, get_model and the print query are as modelled; a pin in its hole across a joint is a fit; the kernel verifies nearly every such pose (D51), and a pair it cannot verify is in `cleared` (clear by a mesh nobody verified; D50, which replaced the advice to ask a refused pair again a little to the side) or in `failed`; a pair in `failed` is neither clear nor colliding and its message says what the kernel computed and could not verify; the axes of joints are best laid along the axes of the model, because askew a pair costs seconds.

**The robot descriptions (D59).** No tool of their own: the formats `urdf` and `mjcf` of the export catalog are written by the tool `export` into one folder (the description and an STL per body; the second format into the same folder needs `overwrite`, since the meshes are the same files), with `at` and `after`. Each answer lists the files with their `about` (the description: the tree, the mass, what was left out and what the format does not write). A paragraph of the conventions in `describe_api` says what the AI needs: the drive fields for URDF, the mass rule, MJCF for MuJoCo, `collision: "none"` for a nested assembly, `view_image` with `after`.

**Inserting a document (D62).** The section `documents`, its three commands and the feature type `insert` go through `execute`, `preview` and `after` and are described by the generated parts of `describe_api`; by hand: the tool `insert_document` (above), `get_document` with the stored documents shortened and `stored`, `save_document { stored, path }` (writes the stored document as a document file of its own, which loads alone; `path` is required with it), `get_model` with `documents` (per stored document its ID, name, the values of its parameters, the number of features and `usedBy`), and a paragraph of the conventions (what an insertion brings, its prefixed IDs and face names, the values of the parameters, the inherited body properties, the warning `insertedIssues`). Guards: `packages/mcp/test/insert-document.test.ts`, the rows of `insert_document` under `execute` and of `save_document` with `stored` in `coverage.test.ts`, and the tool list of `server.test.ts`.

**The import of a mesh (D55).** The section `meshes`, its two commands and the feature type `mesh` go through `execute`, `preview` and `after` and are described by the generated parts of `describe_api`; by hand: the tool `import_mesh` (above), a generated section *Import formats* of `describe_api` from `IMPORT_FORMATS` (`importFormats` of `api.ts`: the title, the summary, the extensions and the options of each), a paragraph of the conventions (an imported body has one face and no edges, no feature changes it, it is made a reference part with its mass, a real collision with a large mesh is slow), the sentence of *Sections of the document* that a change of a section recomputes no geometry gets the exception of a stored mesh, `get_document` without the data of a mesh and `get_model` with `meshes` (above). `changesDocument` compares the parts of two documents but the features only when they are other objects, so a stored mesh is not written out as JSON when it is the same; `addMesh` and `removeMesh` at the top of a call are decided without a preview (a free ID; a stored mesh nothing places), which would check the mesh once more before the command does. Guards: `packages/mcp/test/import-formats.test.ts` (two tables typed by the map of formats, the tool through the server, the ID from a file name, the omission in `get_document`, `get_model`), the row of `import_mesh` under `execute` in `coverage.test.ts`.

**The parts list (D57).** No tool of its own: the query `partsList` is reached by `query` (`{ query: 'partsList' }`, with `at` and `after`) and the format `partsCsv` by `export` (`{ format: 'partsCsv', path }`); `describe_api` lists both from their entries. The query says `geometry: 'modelled'`, so the tool puts no note about a pose beside its answer; `mass` and `totalMass` are printed to six significant digits at any depth (also under `totals`), counts as they are. A paragraph of the conventions of `describe_api` (`CONVENTIONS` in `api.ts`) says what to write into the label of a hole: the name of the piece that goes into it, with what the catalog does not know; for a plain clearance hole the screw, or no label when the screw is counted by the hole of its head or nut; one screw through two parts as one hole feature with both targets; parts held by one screw and copied should touch along the hole or have it cut after the copies; a screw modelled as a reference body has no label on its hole; model what every copy should have before the pattern; every copy counts.
