# Architecture: the repository

Part of [architecture.md](../architecture.md), the design as implemented. Packages, the modules of the engine and of the app, and which may import which.

## Structure of the repository

A pnpm workspace. The boundaries are thereby enforced physically: `engine` has no dependency in its `package.json`.

```
packages/
  engine/            the core, plain TS
  solver-planegcs/   adapter of SketchSolver
  kernel-manifold/   adapter of SolidKernel
  deflate-pako/      adapter of Deflater over pako 2.1.0 (D54): compression of the parts of a 3MF
  scenarios/         validation scenarios against the real adapters (tests only)
  app/               the demo UI + renderer (three.js)
  mcp/               the interface for AI: the MCP server and the bridge to the running app
```

Modules of the app (`packages/app/src`), run by `pnpm dev`:

| File | What it holds |
|---|---|
| `app.ts` | The class `App`: the state of the UI (the mode, the selection, the marker, what is hidden), `refresh`, the toolbar, the timeline, the pointer and key events and their dispatch, the pick in the view, the bridge to MCP. It implements the hosts below |
| `host.ts` | `PanelHost`: what a panel or a form may use of the app. A module of a panel imports this interface and never `app.ts` |
| `features/index.ts` | `FEATURE_UI`: one entry per feature type of the engine, complete by the compiler (how the type starts, how it is edited, its lines in the model panel, its faces, its eye on the timeline, its form), and `TOOLBAR`, the order of the buttons |
| `features/draft.ts` | What the forms share: the mode of a draft (`DraftMode`, which carries its form), the preview and the pause of a slow one, numeric fields, the buttons |
| `features/<type>.ts` | The entry of one type; for the extrusion, the plane and the pattern with the form (`FeatureForm`: the draft and its defaults, the command, the panel, what it wants picked in the view, asked of its state at every pointer event, what a move and a click mean, what it draws) |
| `panels/model.ts`, `parameters.ts`, `sketch.ts` | The panels, as functions over the host |
| `panels/outline-draft.ts` | The import of an outline in the panel of a sketch (D72): the button and the file input, the draft with the report (layers, unit, weld read again), *Place*, and *Replace file…* with the revision and the constraints that hold what goes |
| `panels/body.ts` | The properties of a body (D48): the line of a body, the form of a selected body, the entries whose body is gone |
| `panels/documents.ts`, `features/insert.ts` | The stored documents (D62): their lines in the model panel, a revision from a file, the removal of an unused one; the form of an insertion (the stored document or a file read into one, the frame and the numbers shared with `features/mesh.ts`, the values of the parameters, the bodies that come in) |

| `panels/mechanism.ts`, `pose.ts`, `axis-picker.ts` | The mechanism (D49): the panel (the tree of links and joints, the value of a joint with its slider, *Reset pose*, the forms of a link and a joint); the pose of a body for the view, a pick and a picture; the picker of an axis, shared with the form of the pattern |
| `panels/query.ts` | The generic form of a query (D39): the menu of the queries of the catalog, the form built from the description of the arguments, asking, the life of an answer, the tree of an answer without a view. Its state (`QueryPanel`: the open query, its draft, the armed control, the answer) is an object the app holds |
| `queries/controls.ts` | `CONTROLS`: a control per kind of argument, typed over the kinds, so a new kind does not compile without one |
| `queries/index.ts`, `queries/measure.ts`, `queries/interference.ts`, `queries/section.ts`, `queries/gap.ts`, `queries/print.ts`, `queries/sketch-contacts.ts`, `queries/sketch-sources.ts` | `QUERY_VIEWS`: the optional view of a query (rows in place of the tree, additions to the scene, the note), and the views there are; the collisions are the view of `interference`, the cut model the view of `section`, the contacts of a sketch the view of `sketchContacts`, the sources a sketch can project from the view of `sketchSources` (D69) |
| `references/index.ts`, `references/spec.ts`, `references/edge.ts`, `references/pattern.ts`, `references/projection.ts` | `REFERENCE_UI` (D64): the row of an entry of `external` in the panel of the sketch by its kind, typed by the union of the kinds, so a kind of the engine does not compile in the app without its row; the entities of the entries for the pickers (`entryEntities`, `entryTag`) and what the view marks for a hovered entry (`hoverMarks`) |
| `sketch-mode.ts` | The sketch mode: what the events of the view mean in it (the place under the pointer and its snap, the inferred direction, the places kept, the hover of an edge, Escape and Enter), the drag of a point, what it draws (`SketchHost`); the rest of a tool is its entry of the table |
| `sketch-tools/index.ts`, `sketch-tools/spec.ts`, `sketch-tools/<tool>.ts` | `SKETCH_TOOL_UI` (D64): one entry per tool of the sketch bar in the order of the bar, its keys `SketchToolName`; the shape of an entry (`SketchToolUi`: what it picks, how many places, the click, Enter, what it draws, its options and their panel) and `drawn`, the batch of a drawing tool with the switch of construction curves. A module of a tool imports only types of `sketch-mode.ts` |
| `scene.ts` | The scene of the model: bodies, outlines, planes, the other sketches, highlights (`SceneHost`); what a view of a query adds, and the cut it may make (`shownCut`, read by the scene and by the pick of the app) |

| `sketch-view.ts`, `sketch-commands.ts`, `sketch-diagnosis.ts` | The geometry of a sketch for drawing, hit tests and measuring; the commands of the drawing tools, constraints and dimensions from a selection; the texts of the diagnosis |
| `draw.ts`, `labels.ts`, `fields.ts`, `issue-text.ts`, `dom.ts` | Shared helpers: drawing into a scene, texts, numeric fields with units, issues named for a human, the DOM |

A new feature type costs the app a file in `features/` and a line of `FEATURE_UI`; without the line the app does not compile. A new tool of the sketch bar costs a file in `sketch-tools/` and a line of `SKETCH_TOOL_UI`. The test `packages/app/test/app.test.ts` drives the class as a user does and compares a record of every step with snapshot files (see `docs/d36/00-prep/part3-app-panels.md`). `packages/app/test/query-controls.test.ts` drives the controls of the form of a query that no query of the catalog reaches yet.

The imports go one way, in the order of the table: the leaves, then `sketch-content`, then `validation`, `schema` and `sketch`, then `mesh`, then `recompute/*`, then `references/*`, then `features/module`, `features/profile` and `features/extent`, then the modules of the types, then `features/index`, then `sections/*`, then `document.ts` and `evaluate.ts`, then `sketch-cut.ts`, then `query/*`, `export/*` and `import/*`, then `sketch-tools.ts` and `engine.ts`. A module of a feature type imports neither the registry, nor `document.ts`, nor `evaluate.ts`; what it has to ask the registry (does the target of a reference exist, is it of the right kind and before this feature) reaches its validator as `context.requireRef`. `document.ts` and `evaluate.ts` re-export what moved out of them, so the import paths of the tests and of the other packages did not change. `packages/engine/test/modules.test.ts` guards the direction: it reads the imports of every module with the TypeScript parser and fails on a cycle among those that load a module at run time. Only a statement that is type-only as a whole (`import type`, `export type … from`) is left out: with `verbatimModuleSyntax` a statement whose names are each marked `type` still loads the module. It also loads every module as the first one, which catches a module that reads another at its top level before that one is set.

Modules of the interface for AI (`packages/mcp/src`): `tools.ts` (the tools over the engine, with no dependency on Node or the browser), `host.ts` (the registry of operations of the app and the entry that runs one, shared by the server and the app), `view-image.ts` (the operation `view_image` and the capability of the view it asks; the app imports it as `@trymesh/mcp/view-image`), `export-writer.ts` (the writer of exported files, for the server), `api.ts` (the description of the API generated from the sources of the engine), `server.ts` and `main.ts` (the MCP server and its start), `bridge.ts` and `bridge-client.ts` (the bridge between the server and the app). It is built by `pnpm mcp:build`; it is the only package bundled into one file, because Node runs it without Vite.

An adapter imports only types of the engine (`import type` from `@trymesh/engine`), with one exception: `solver-planegcs` imports the function `commonEnd` (`common-end.ts`, the leaf above), so that the adapter and the analysis of the sketch read one rule of a tangency at a common end (D72). `modules.test.ts` holds both: `common-end.ts` imports nothing at run time, and no adapter imports another value of the engine.

The adapter packages are the only places that import a library behind a port: `solver-planegcs` (`@salusoft89/planegcs`), `kernel-manifold` (`manifold-3d`) and `deflate-pako` (`pako`, from `pako/lib/deflate.js`, with the one function it calls declared in `src/pako.d.ts` because the package has no types). The app and the server compose them in their `main.ts`; `packages/mcp/package.json` names `pako` too, because the bundle of the server leaves third-party libraries outside and Node finds them from `packages/mcp/node_modules`.

Tests: Vitest (`pnpm test`), type check `pnpm typecheck`. The validation scenarios run in Node against the real adapters. The packages are not built: each exports its TypeScript source directly.
