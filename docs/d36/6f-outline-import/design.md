# 6f Import of an outline (D72)

**State: designed 2026-11-25 on Fable, with prototypes run against the real engine and adapters; reviewed in three rounds the same day (Fable with probes, `codex`, and `agy` in the first two) and revised after each ("Reviews"); the owner's answers to "Open" 1 and 2 given on 2026-11-25, each as recommended (answers 37 and 38 of [6-cross-review.md](../6-cross-review.md)); not implemented.** The text is written against `master` at `c01e765` (schema version 10), where every package before 6f in the sequence of step 6 is implemented and merged: 6a (D64), 6a2 (D71), 6e (D65), 6c (D68), 6b (D69) and 6d (D70) ([6-plan.md](../6-plan.md)). It reads their code, not their first designs; "What 6f needs of the packages before it" checks each thing their designs say of 6f against the code.

Files: [contract.ts](contract.ts) (the entry, the stored value, what the registry gains, the import and its two formats, what 6f adds to the packages before it, the query, MCP, the app), [calls.ts](calls.ts) (validation scenario 15 as one model, and the cases of 6f), [probes/](probes/) (the prototypes behind "Measured", kept so that every number can be run again).

The package in short:

1. **A reference kind of entry of `external`, `outline`**: the curves of a drawing (lines, arcs, circles, splines) stored **in the entry**, in the coordinates of their file, and placed in the sketch by three numeric fields (`x`, `y`, `turn`) and an anchor (the origin of the file, or the centre of its box). Fixed for the solver, so constraints may name its entities and a later sketch may project them.
2. **Entities `<entry>/<local>`** (a curve, `board/l3`) with points named as an own curve names them (`board/l3/a`, `board/a1/center`, `board/s1/0`). The readers number the curves by the kind the file gave and its order: `l1`, `a1`, `c1`, `s1`; nothing after the reader renames a curve.
3. **The flag `regions`, default true** (owner, answer 2): the curves bound regions, their ends join by position in 6c's stage (no code of 6f's), and they name side faces. With the flag off the outline is reference only.
4. **A revised file is `updateExternal` with the new curves**; an entity keeps its ID when the file lists it at the same place among the curves of its kind, and the entry stores what the file was read with (`readWith`: the layers, the unit, the weld), which a replacement repeats. An update that takes away an entity a constraint names is refused (the third part of 6a's rule of an update, which is 6f's to write: without it the document that results does not load, measured).
5. **The stored value is the placement and a fingerprint**, not positions: the document holds every coordinate once. `Projected` stays positions; what `solved.external` holds is `StoredValue`, either.
6. **The solver gets of an outline only what the constraints name**, as it gets the axes of the origin: with a whole outline of 2000 curves in its input the adapter runs out of memory (measured). The points and the radii it did not get are put back after it, on every path of the step. The adapter takes two fixed points at one place for one end, so a tangency at a corner of an outline is solved as one.
7. **The import**: a second catalog of formats, `OUTLINE_FORMATS` (`dxf`, then `svg`), beside `IMPORT_FORMATS`; the function `importOutline` with what every format shares: the IDs, a weld of the open ends that a file with few digits leaves apart, **bounded** in what it moves and in what it costs (no end goes further than the tolerance, nothing is merged in a chain, an arc gives way to another arc only and stays within the tolerance of the arc of the file; a file welds the same wherever it stands), the limits (bytes, curves and control points read; 2000 curves and 2000 control points of splines in an outline), a report. A file that is not whole is refused; what a reader does not read is listed. Hand-written readers, no library.
8. **The MCP tool `import_outline`** reads a path, as `import_mesh` does, and sends the command itself (the curves never pass through the caller); without a sketch it only reports; with `replace` it reads the file as the entry was read, and with `remove` it takes the constraints that hold a revision back out in the same batch. `get_sketch` lists an outline and its regions short, and two queries page through the rest: `entryCurves`, and `sketchRegions`, which gives a region's whole reference (a region of more than twenty curves is named through MCP by its answer). Over the bridge the file travels as base64 to one function that runs where the engine is. The app has *Import an outline…* in the panel of a sketch.
9. **Scenario 15 as one model**: the board imported from a DXF the test writes as a PCB tool would, the cover built on it by the packages before, and the checks of step 7; the whole ran on the prototype.
10. **No command, no feature type, no face role, no issue code, no section, no schema step.**

Not in the plan, found in the code:

- **`solverSetup` puts every point and curve of every resolved entry into the input of the solver** (`sketch.ts`), fixed. Fine for an edge (three points); an outline of 2000 curves is 3000 fixed points, and the planegcs adapter aborts with "OOM" on such an input, depending on what it solved before (measured, C4).
- **`updateExternal` accepts an update that takes away an entity a constraint names**, and the document it leaves is refused by `load` ("entita "pcbo/c4/center" ve skice není"): the slot of 6a's rule in `updateProblem` is empty, with the comment "refused by the package that can reach it, 6f" (measured, B5).
- **`updateExternal` takes the whole entry.** For an outline that is every curve again to switch a flag.
- **The stored value of an entry is typed `Projected`** (`SolveStamp.external`), "positions and nothing else", and it is what the stamp holds of an entry. An outline's positions are its entry's; stored again as a value they would double the document.
- **`contactFix` of 6e finds a flagged projection by `sketch.external[curve.id]`**, which a curve of an outline (`o/l1`) is not: such a curve gets the general reason "is reference geometry, which no tool cuts", and the ends of an own curve at its end, while they are not one vertex with it, are listed as a contact no cut repairs, the defect 6b fixed for its projections (the crossing measured, D1; the ends read from the code).
- **`isSplineOf` of 6b knows an own spline and a copy of one**, so a projection of a spline of an outline is refused with "is a spline, expected line", not with 6d's text (measured, D5).
- **`get_sketch` spreads a reference entry into its answer** and lists every entity with its place (`sketchDetail`, `packages/mcp/src/tools.ts`): for an outline, all its stored curves and then all of them again.
- **A file written with few digits does not close**: the ends of an arc, computed from its centre, radius and angles, and the ends of the lines beside it differ by the rounding of the file, and ends join only within 1e-6 mm (measured, A3: a board written with four decimals is sixteen open ends).
- **The adapter knows a common end of a line and an arc by their IDs or by a coincident** (`commonEnd`, `packages/solver-planegcs/src/index.ts`). The end of a line of an outline and the start of the arc beside it are two IDs at one place, as those of two projections of 6b are. An own line held on the one and tangent to the other curve is solved in the general form at its double root: the far end 4e-5 mm off the tangent, and it does not follow a drag (measured, J10; the review, agy 7).
- **6c's stage counts an end as open when no other curve ends there** (`positionJoins`), so a closed spline of an outline, whose two ends are one point, bounds its region and is listed in `openEnds` with the distance 0 (measured, J9; the review, codex 12).
- **`get_sketch` lists every region with its whole outer loop** (`regionRows`), and `get_document { feature }` returns the feature as it is, past `documentShown` (the reviews, fable 4 and codex 14: 33,841 characters of regions for 1000 curves).
- **The pickers of the app limit a derived entry only** (`PICKER_LIMIT`, `packages/app/src/references/index.ts`): an outline of 2000 curves would be 5000 options.
- **`extend` looks for a spline in its way among own curves only** (`reachOf`, `extendSpec`: `world.sketch.curves[C]`), and `contactFix` asks for a spline before it asks for a flagged curve; the names a cut collects walk every entry of `external` (`namedOutside`). All three read in the code (the review, agy 11 and 13).
- **The names `OutlineCurve`, `Outline`, `export/outline.ts` and `packages/engine/test/outline.test.ts` are taken** (a curve of a closed loop of the profile, and the exported section). The curve of an import is `ImportedCurve`.

## The cheap variant

What the plan asks, with these choices:

- The curves live in the entry; one entry is one file (or the chosen layers of one); the same file in two sketches is two entries, or one entry and projections of it.
- The placement is three numbers and an anchor. No mirror, no scale: the unit is the reader's.
- A revision keeps IDs by kind and order; nothing is matched by geometry.
- An outline is never cut and never copied by a pattern; where it has to be cut, it is drawn as own curves in a later sketch (6b's tool).
- The readers take the listed subset and say what they left out; nothing is repaired but ends that nearly meet.

**Deferred**: STEP and other exact formats, text, matching a revision by geometry (the plan's list); a placement on a point of reference geometry; a mirrored placement; an own outline drawn over an import in the same sketch by a tool (a later sketch does it; a backlog row with 6b's "an existing projection taken over as own curves"); periodic and rational splines (a periodic one could be read by clamping it first, which gives the curve exactly: the review's probe; a backlog row), splines of a degree above 3, ellipses and elliptical arcs; blocks of a DXF (`INSERT`), nested `svg` and `use`; CSS of an SVG (a hidden element is read); a file kept linked to its path (the document stores the curves, not where they came from); an outline from a face of an imported mesh.

## Measured

**Recipe.** `npx vitest run --config docs/d36/6f-outline-import/probes/vitest.config.ts` from the root of the repository (one file: add its path), against the real engine, the real planegcs adapter and the real manifold kernel; 86 cases in 14 files, about 75 s. The numbers go to the console. The prototype holds the kind, put into `REFERENCE_KINDS` at run time, the weld and the IDs (`probes/proto.ts`), the reader of DXF (`probes/dxf.ts`) and the reader of the SVG subset (`probes/svg.ts`); `probes/cover.ts` the cover of scenario 15 over the imported board. The reader of stored values (`projected`, `references/spec.ts`) is mocked to take the form of an outline's value. What the prototype does not have: the solver's input narrowed inside the engine (probe F emulates it at the port: a solver that takes the unnamed fixed geometry out, solves, and puts the positions and the radii back; the review built it inside the engine, rows R below), the third part of the rule of an update, the partial update, the fixed join of the adapter, the condition of 6c's stage, the texts of 6e's reasons, the stored `readWith`, the report's `ids` and notes, the two queries, MCP and its bridge, the app. Timings are of one machine and one file run alone, to compare with each other; under the whole set they are about twice as long. **They are measurements of these files, not bounds**: the cost of an outline follows what it holds (rows C and J12).

The weld, the validator and the readers of the prototype were rewritten after the review; rows A3, A4, D5 and H4 are of the revised prototype, rows I, S and J are new, and rows R are the review's own probes (Fable; its files are not in the repository, its numbers are quoted from its report). After the second round the weld was rewritten once more (rows J3 to J5 are of it, rows K are new), the validator enforces what the design says of it, and both readers were tightened (rows I10 and S10 to S14).

What the numbers decide:

- **The reader welds** (A3): a file of four decimals, which is what a drawing has when its units are written to a tenth of a micron, does not close without it. The default is 0.01 mm: it closes every file down to two decimals of a millimetre and four of an inch.
- **The weld is bounded, and touches only what is open** (J1 to J5): an end that another curve meets within 1e-6 mm is never moved, so a file that closes is not changed, however short its curves; an open end goes onto one other end, never further than the tolerance from where the file had it; a chain is not followed. That is what makes 0.01 mm a safe default: it is not a claim about how short the curves of an outline are. What it could not close is counted and listed.
- **An end of a line goes to the end of an arc, never the other way** (A3, A4, J4, K2): arcs keep the digits of their file. Only where two arcs meet does one give way, as the circle through its new ends and its old middle, when the arc of the file stays within the tolerance of it (J5, K11). Its radius is not bounded: a shallow arc written with few digits does not hold its radius, and the report says by how much it changed.
- **The weld costs by its curves, not by their pairs** (K6, L7): 65 ms for 2000 strokes that do not meet, where the first revision took 14.5 s; ends in a cluster are left alone; curves that share one place are not compared with each other.
- **A file welds the same wherever it stands, and nothing the weld answers is refused by the validator** (L1 to L3): held over 2200 generated rings at three places each, over rings up to 500 km from their origin, and over 3000 files at the scale of the join.
- **The IDs are the reader's** (K1): they depend on the file and the layers, not on the weld and not on what is left out.
- **An arc of nearly a whole turn is a circle** (J3), and a curve twice in a file is read once (J6): both are ordinary in drawings, and both gave an invalid or a wrong profile without a word.
- **The solver gets what the constraints name** (C2 to C4, F1, R1): not for the time (14 ms of 60) but for the memory, which is not ours to bound: the same input solved or aborted by what the adapter had solved before. Built inside the engine by the review, it gives the results of the whole input.
- **The limits are 2000 curves and 2000 control points of splines** (C1, F1, J12): a spline costs by its samples. 2000 lines and circles are 120 ms to place and 100 ms for every change in that sketch while they form regions; 500 splines of four points 115 and 68 ms; 31 splines of 64 points 118 and 110 ms; with the flag off 5 to 17 ms. Without the second limit 2000 splines would be 440 ms a change. Above 500 curves the report of an import says what a change in the sketch will cost and that a later sketch, which projects what it needs, costs nothing of it.
- **A reader refuses early** (I8, S9): by the characters, the curves and the control points it has read, before any weld.
- **The value is the placement and a fingerprint** (A2, B1): 80 characters, whatever the outline.
- **`get_sketch` lists fifty curves and fifty regions** (C1, R7): 4000 characters of lines and circles; the whole of 1000 curves would be 79,000, and their regions 34,000 more. The curves listed are bounded by their positions too (a spline of 64 control points is 64), and a loop printed short names the query that gives it whole.
- **The update needs its rule** (B5): today a legal command leaves a document that does not load.
- **The anchor `center` is what "symmetric about the axes" asks for** (B1, B3): the page coordinates of the file do not reach the model, and the revised board stays on the axes.
- **The adapter has to know that two fixed points at one place are one end** (J10, K12), or the corner an own line is most likely to start from gives a tangency that is 4e-5 mm off and stiff. "One place" is by the radius of the arc, so nothing changes for points that are only near (K12), and nothing changed in any test of the repository (R10).
- **The packages before need four conditions and three texts** (B2, B4, D1 to D4, G1, H1 to H5, J9, J10): nothing of 6b's kind or tool; in 6c's stage a closed curve; in 6e's module the order of two questions and where a spline is looked for.

## Decisions

### The stored outline: in its entry

The curves of an outline are a field of its entry, `external.<id>.curves`, and nowhere else.

- **Why not a section** (`outlines`, as `meshes` of D55, which the plan sketched). 6a requires that `entityOf` answers from the sketch alone. With the curves in a section, every entry that places an outline would hold a copy of the list of its entities, kept equal to the section by every command that touches either: `addOutline`, `removeOutline`, a replacement that reaches into every sketch that places it, a check on `load`, and the rule of a constrained entity asked across the sketches of the document. A section also needs a schema step. The gain would be one outline placed in several sketches, which a projection from the sketch that holds it gives already, with one place to revise.
- **What it costs**: the entry is as large as the file (823 characters for the board, 140,000 for 2000 curves). Every command that changes the sketch makes a new sketch object and shares the entry's; undo shares it too. `get_document` leaves the curves of a large outline out, as it leaves out the data of a stored mesh.
- **Size limits**: 1 to 2000 curves; a spline 3 to 64 control points (6d's limit), the splines of an outline 2000 together; positions finite. An import beyond a limit is `tooLarge`, an entry beyond one an invalid command. The limits bound what the measurements cover; they are not a promise of a time.
- **A local ID** is letters, digits and underscores, at most 32, and no name every object has (`__proto__`, `constructor`, `toString`: the rule of `newId`, `validation.ts`). Measured before the rule: a record parsed from JSON with the key `__proto__` was accepted and stored with no curve. The look-up of a curve by its local ID asks for an own property.
- **The form**: `curves: Record<local ID, ImportedCurve>`, in the order the reader made them; an `ImportedCurve` is a line (`a`, `b`), a circle (`center`, `radius`), an arc (`center`, `start`, `end`, counter-clockwise) or a spline (`points`, the control points of a spline of 6d), with positions `[x, y]` in millimetres in the coordinates of the file. A position is a number, never a field: an expression there is an invalid command.

### The entry `outline`

```ts
interface SketchOutline {
  type: 'outline';
  name?: string;                        // of the file, for people
  readWith?: { format; layers?; unit?; weld? };  // what the file was read with
  curves: Record<Id, ImportedCurve>;    // in the coordinates of the file, mm
  x: number; y: number;                 // where the anchor lands, numeric fields
  turn: number;                         // rad about the anchor, a numeric field
  anchor: 'origin' | 'center';          // the origin of the file, or the centre of its box
  regions: boolean;                     // the curves bound regions; default true
}
```

- **`regions` is always in the document** (6b's convention); `addExternal` may leave it out and gets `true`. So may it leave out `x`, `y`, `turn` (0) and `anchor` (`origin`).
- **It has no reference**: `refs` and `faces` are empty, nothing of the model is read, and `compute` cannot fail. An outline has no warning of its own.
- **One file, one entry.** Two entries may hold the same curves; on each other they make the profile invalid as any two curves do, and `sketchContacts` lists the pairs (measured).
- **`readWith`** is what the import was made with: the key of the format and the options as given. The IDs of an outline depend on the layers chosen, and its size on the unit, so a replacement has to read the revised file as the first was read; stored nowhere, they were forgotten, and the scenario's own file replaced with every layer gained two lines and two open ends (the review, fable 3 and codex 8; R9). Optional: an entry written by hand has none. Checked by its form only; a field of a new kind, so no question of the schema.

### Entities and their IDs

| Curve of the entry `o` | Entities |
|---|---|
| a line `l3` | `o/l3` (line), `o/l3/a`, `o/l3/b` |
| a circle `c1` | `o/c1` (circle), `o/c1/center` |
| an arc `a2` | `o/a2` (arc), `o/a2/center`, `o/a2/start`, `o/a2/end` |
| a spline `s1` of n control points | `o/s1` (spline), `o/s1/0` … `o/s1/<n − 1>`; a closed one lists its first point once |

- **The entry itself is no entity** (as the entry of a mirror is none): `o` names nothing a constraint could take.
- **Points belong to their curve**, named as 6b's projection names them (`<curve>/<name>`), and two curves that meet have two points at one place. This leaves 6a's vocabulary, which gave an outline points of its own that its curves share ("What 6f changes in 6a's vocabulary"). Since answer 19 the ends of curves that are not own join by position anyway, so shared IDs would close nothing more; and a point named by its curve keeps its ID exactly when the curve does, where a numbering of the vertices of a file would shift with every vertex added.  What it costs is one case of the solver, a tangency at a corner, cured in the adapter ("A tangency at a corner").
- **The local IDs are the reader's**: `l<n>`, `a<n>`, `c<n>`, `s<n>`, each kind counted from 1 in the order of the file, after the choice of layers, **from the curves as the reader gave them and before anything else**. Nothing after that renames a curve:
    - A curve that is left out (it has no extent, or it lies on an earlier one) leaves its number unused.
    - An arc of nearly a whole turn that the weld reads as a circle keeps the ID the file gave it: `a3` is then a circle, with the entities of a circle (`o/a3`, `o/a3/center`). The letter says what the file had; the `type` of the curve says what it is. The first revision said "before the weld" and numbered such a curve among the circles, so one near-whole arc renumbered every circle and arc after it by the weld option (all three reviews; measured after, K1: the same IDs for every weld).
    - So the IDs depend on the file and the layers, and on nothing else. A polyline is its segments, counted with the rest; a segment between two vertices at one place is no curve and takes no number.
- By kind, so that a hole added to a board moves no line and no arc. An entry written by hand may use any local IDs.
- **When an entity changes its kind under its ID** (that arc, a circle in one revision and an arc in the next, because its gap grew past the weld): the update is taken when no constraint of the sketch names the entity, and refused, naming the entity, both kinds and the constraints, when one does ("A revised file"). A later feature that names it breaks aloud, as for an entity that went: a projection of 6b says "is an arc now, not a circle" and keeps its place.
- **`entityOf` asks the kind for one ID** (`entity`, a member the derived half has since 6c and the reference half gets): `o/l3/a` is two look-ups, not a listing of 5000 entities. `entities` stays for the listings (`entityIndex`, built once per sketch object). The own rule of a constraint asks the same way for the points of a curve (five names), and the rule of an update for each operand.
- **What a region and a face are named by**: the curve's ID, `{ outerLoop: ['o/a1', …, 'o/l4'] }` and `{ feature, role: 'side', curve: 'o/l3' }`; the key of such a face quotes the slashed ID (6c wrote the quoting).

### The placement

- **`x`, `y`, `turn`** are numeric fields at `external/<id>/x`, `…/y`, `…/turn` (mm, mm, rad within a turn either way): they take expressions, `setField` with the sketch as the feature changes one, and the recompute follows a parameter (measured).
- **`anchor`** says which place of the file lands at (`x`, `y`), and the outline turns about it:
    - `origin` (the default): the origin of the file. The file's coordinates are the model's but for the motion; a revised file moves nothing that did not move in it.
    - `center`: the centre of the box of the curves (lines by their ends, circles whole, arcs by what they pass, splines by the box of their curve). The outline is centred whatever the page coordinates of its file, and stays centred when a revision is larger. This is how the board of scenario 15 is symmetric about the axes.
- **A point p of the file stands at `at + R(turn) · p`**, with `at = (x, y) − R(turn) · a` for the anchor `a`. A turn of exactly 0 multiplies nothing, so an outline that is not turned keeps the digits of its file up to the addition of `at`.
- **Not a point of the sketch** (the review's finding 9), and **not a point of reference geometry**: an entry would then depend on another, the order of `resolveReferences` (by ID) would matter, and an outline could fail and would need a frozen value, which is its positions. A place that follows a body is an expression over parameters today; "Deferred".

### The value, the stamp, the arcs

- **The value** of an outline in `solved.external` is `{ kind: 'outline', at, turn, data }`: where the origin of the file lands, the turn, and `fingerprint(stableStringify(curves))`, computed once per object of `curves`. It is not positions, and `Projected` stays the four forms of positions: what the stamp holds per entry becomes `StoredValue = Projected | PlacedOutline`, read by `storedValue` in the place of `projected`. So the code of 6b that holds a `Projected` never meets a form it cannot have (the review, fable 11; the first design made it a fifth form of `Projected`).
- **The stamp** of the sketch holds the value, as for every reference: it changes when the outline moves or its curves change, and not when its flag, its name or its source does (measured by the review, R1). With the stamp kept the stored positions of the own points are used; the solver still runs for the diagnosis, as at every step.
- **Nothing is frozen**: the value never fails, so `value` (the reader of a stored one) only checks the form.
- **`keepsValue`**: an update keeps the stored value when it changes neither the place (`x`, `y`, `turn`, `anchor`) nor the object of `curves`, and drops it otherwise, as 6b's kind does. The reviews differ here. Fable: always keeping it is safe, because the stale value is never used as a frozen one and the stamp differs, so the recompute writes the fresh one. agy: a document saved while its sketch is in conflict (nothing is written back then) keeps the value of a placement the entry no longer has. Both are right; the second costs nothing to avoid, so the value is dropped.
- **The geometry** is computed from the entry and the value (`outlineGeometry`) and kept per entry object (a `WeakMap` by the entry, with the ID and the value it was made for), so a drag of an own point does not place 2000 curves again (measured: 0.00 ms), and two entries that share an object of curves do not push each other out of a cache of one slot (the review, agy 10). A switch of the flag makes a new entry object and places the outline once.
- **Arcs.** A stored arc has its two ends on one radius within 1e-9 mm per mm of its largest coordinate, at least 1e-9 (the tolerance of 6b's stored arc; an absolute one is under the last digit for coordinates of 1e5 mm: the review, fable 16), **and never more than 1e-7 mm**, a tenth of the join (the third round: "Validation and the commands"); the validator refuses more, with the distance. The readers leave under 1e-12 near the origin of the file. The placement then puts the end on the circle of the start (6b's `exactArc`, shared), so a fixed arc is as exact as the solver asks (1e-10; measured 4e-15).
- **A spline** of an outline is a spline of the result over its control points (`{ type: 'spline', points: ['o/s1/0', …] }`), which 6d's shape function takes from any source: it forms regions, names a side face, and no constraint names it; its control points are points like any other of the entry.

### Regions, joins and face names

- With `regions: true` every curve of the entry is in `EntryGeometry.regions`; with `false` none. Never some: the layers of a file that should not bound anything are left out at the import, or go into a second entry with the flag off.
- **The ends join by position** in 6c's stage (`positionJoins`), which takes every curve that is not own and forms regions: with each other within 1e-6 mm, and with the end of an own curve that forms regions there, when the own ends at that place are one vertex. Nothing is stored. The reader's weld is what makes "within 1e-6" true for a file.
- **One condition in that stage**: a curve whose two ends are one place is closed and has no open end. A closed spline of an outline bounds its region today and is listed in `openEnds` all the same, with the distance 0 and the advice of an open end (measured, J9; the review, codex 12). The first design said 6f writes no code there.
- **An own chain may close an open outline** (measured, D2): own ends `coincident` with the open ends, one region of own and imported curves.
- **Ends that stay open** are in `SketchResult.openEnds` (6c), `apart` with the nearest end and how far; the advice of `get_sketch` gets the cure for an outline: import again with a larger `weld`, or end an own curve there.
- **Invalid, as for any curves**: an own curve that forms regions and crosses the outline, two outlines on each other, curves of one file that cross. The first has no repair by a tool ("At the plug-in points of 6e").

### The solver gets what the constraints name

- A kind may say **`narrow`**: the input of the solver gets of its entries only the entities that a constraint of the sketch names: a named curve with its points and its radius, a named point alone. An outline says it; the kinds of today do not, so the stamp of every stored sketch stays (measured by the review, R1: identical).
- **Where**: `resolveReferences`, which has the sketch, gives such an entry `solver`, the part of its geometry the operands of the constraints name (reference dimensions too: they are measured from the curves of the input); `solverSetup` reads `solver ?? geometry`. The curves of the sketch, the profile and the result read `geometry`, whole.
- **After the solver** the step puts the points **and the radii** of the entries into its geometry, as it puts the far points of the axes there: the solver returns only what it got, and a circle of an outline that no constraint names, or whose centre alone is named, has no radius without it and is no curve of the profile (`placedCurve`, `sketch.ts`; all three reviews, agy as a blocker: the first design said "positions", and the emulation of probe F merged both, so its result did not show it).
- **On each of the three paths** of the step: solved with a new stamp; the stamp kept, where the geometry is the stored input; a failed solve. One place after the three, not in each.
- **In one order**: the merged records of points and radii are built own geometry first, then the entries by ID, whatever is named, so the order of the keys of `SketchResult.points` does not follow which entities are constrained (the review found the values equal and the order not).
- **Sound** because every point of reference geometry is fixed and no equation of the solver reads a fixed entity that no constraint names; the analysis of freedom counts only variables that are not fixed. The adapter's spread and the analysis take their extent from the points of the input, so they see the named points only; the review compared the whole `diagnoseSketch` and found it equal. The stamp then holds, of an outline, the named curves and the value, which is everything the solve depends on.
- **No bound when constraints name most of an outline**: the solver then gets what they name. A constraint is made by hand or by a tool, one at a time; a sketch with a thousand constraints on an outline is as large as one with a thousand own points.

### A tangency at a corner

- The points of an outline belong to their curves, so at a corner the end of a line (`o/l1/b`) and the start of the arc beside it (`o/a1/start`) are two fixed points at one place, with no coincident between them (a constraint between fixed entities is refused, and would never take effect). The same holds for two projections of 6b that meet.
- The adapter chooses the form of a tangency of a line and an arc by whether they share an end (`commonEnd`: one ID, or one coincident that names an end of each). An own line whose start is coincident with `o/l1/b` and that is tangent to `o/a1` shares the end in fact and not by any ID: the general form is taken, which has a double root there. Measured (J10, K12): no conflict and no redundancy is reported, the far end of the line is 3.7e-5 mm off the tangent, and it does not follow a drag. The app's hit test gives the point of the line at a corner (the lines of an entry are listed before its arcs), so this is the case a user meets. The other way round, an own arc held on the point of the corner arc and tangent to the outline's line, is off too (1e-7 mm; the review measured 1e-5 before a drag).
- **The rule, stated as an equivalence** (the second round: fable 9, codex 3). Two ends are *one end* when they are one ID, or two fixed points at one place. A line and an arc have a common end when an end of the line and an end of the arc are one end, or when one coincident names two points that are one end with an end of the line and with an end of the arc. It reads the same from either side: the own line held on the outline's point of the other curve, the own arc held on it, and an own line that starts at `origin` where a fixed arc starts.
- **One place is at most 1e-6 mm, and for a fixed arc also within 1e-6 of its radius** (`sameEnd`). The first revision said 1e-6 mm. That is right for a board and wrong for a fixed arc of radius 1e-4, where a point 5e-7 mm inside the start is half a hundredth of the radius away and no tangent passes through it (codex's case: the adapter and the analysis then disagree). By the radius, such a point is not taken and the sketch is solved as today (K12, at radii 3, 0.01 and 1e-4).
- **When the arc is own, 1e-6 mm alone.** Its radius is a variable, and the second revision's rule read it from the estimate: an own arc held on one of two fixed points 8e-7 mm apart was at a common end while its radius was 0.9 and not at 0.7, so a drag changed the form of the tangency (the third round, fable 7; R13). The two fixed points are both held and at most the join apart, so the common-end form is off the exact tangent by no more than that, whatever the radius becomes; codex's case was a fixed arc.
- **The adapter and the analysis agree where the rule applies.** The analysis takes the common-end form when the end of the line lies on the circle within 1e-6 of the size of the curves (`SHARED`) and is held there. A point within 1e-6 of the radius of the arc's end is within that of the circle, and it is held, being coincident with a fixed point: whenever the adapter takes the common end, the analysis does. Where the adapter does not (a point near and not at the end), the two differ as they do today; nothing is made worse.
- **Nothing changes in what exists** (the reviews' probes, R10 and R12): with two fixed points within 1e-6 mm taken as one end, and again with the rule by the radius, the 2638 tests of the repository and the four spikes of the solver pass, and no decision of `commonEnd` differs. The widening no test reaches, an own line from `origin` where a fixed arc starts, was run in the patched adapter: exact where it is 2.8e-5 of the radius off today, and it follows a drag (R12). A document solved by today's adapter loads with its stamp and its stored positions (3.7e-5 off); the first change after gives the exact place.
- **A chain is not read**, as today (D52: "a chain of joins is not read"): an own line and an own arc, each coincident with another of the two fixed points of a corner and tangent to each other, are joined through two coincidents (agy's case). The same chain through one fixed point is not read today either; widening that changes decisions for sketches that have no outline, and belongs to D52, not here. A known limit.
- `commonEnd` reads positions now (its comment says "never from positions"): of fixed points, and the radius of the arc only when the arc is fixed too. Each is a number of the input and never a variable of the estimate (the second revision's sentence "of fixed points only" was not true of the radius of an own arc). It is given the points, the fixed set and that radius. With the narrowed input both points are in it: the one the coincident names, and the end of the named curve.
- Not by giving up the points per curve: shared vertex IDs would need a numbering of vertices that a revision shifts ("Entities and their IDs"), and the case exists for 6b's projections without any outline.

### A revised file: the update and its rule

- **A revision is `updateExternal`** with the new `curves`. `partial` (below) lets it send nothing else, so the placement, the flag and their expressions stay.
- **What keeps its ID**: an entity whose curve is at the same place among the curves of its kind in the new file, read with the same layers (`readWith`). A board made wider keeps every ID; a hole added at the end of the holes adds `c5`; a hole added first renames the others; two holes listed the other way round swap (measured).
- **What a revision did to the IDs is told** (`outlineRevision`; the reviews, fable 13 and the second round):
    - `kept`, the IDs both outlines have, and `changed`, those of them whose curve is at no place the old outline had a curve (it moved, or it is another curve under an old ID);
    - `added` and `removed`;
    - `renamed`: an ID, old or new, whose curve is where the old outline had the curve of another ID. Two holes swapped are listed (J11). A hole put in first gives every later hole the next number, and each is listed, the last one too, which is a new ID and so also in `added` (K10; the first revision left it out and called the old `c4` added).
    - Places are compared by distance within 1e-6 mm, in the cells around them and not by one rounding (two places 2e-15 apart across the edge of a cell are found, K10), a line and a spline either way round. A curve that moved and changed its place in the file at once is `changed`, not found. No matching by geometry is done with any of it: the caller is told, the IDs stay the file's.
- **The rule of an update, its second and third part** (`updateProblem`). When the kind of either entry answers `entity`, the one before or the one after (an edge updated into an outline, or back), both are one pass over the constraints of the sketch, driving and reference: for each operand that is the entry's ID or under it, the kind before and the kind after.
    - Gone: refused, naming the entities and the constraints (the third part, which 6a left to the package that reaches it).
    - Another kind: refused, naming the entity, both kinds and the constraints (the second part; its text today is Czech and names nothing).
    - An entity no constraint names may go, come or change its kind.
    - The operand that is the entry's ID itself counts (an edge or a projection updated into an outline: `e` was a line and is no entity of an outline; the second round, agy 7). Nothing is listed: no 5000 entities of either entry.
    - The kinds without `entity` keep the second part as it is (any entity that stays keeps its kind), by their two short listings.
- **The way past it is one batch**: the constraints removed, then the update. A batch is atomic and its commands see the sketch as the ones before left it, so this order passes and the other does not. Through MCP the tool `import_outline` takes `remove`, the constraints to remove in its batch (the reviews, codex 9 and fable 6: the first design told the caller to use a batch and gave the tool none, so the constraints were removed in one undo step and the replacement refused or made in another). The app's draft offers the same as a checkbox.
- **What is not refused**:
    - An operand of a mirror or pattern of the same sketch (its axis, direction or centre) that goes away: the entry loses its copies with the warning `brokenCopies`, and the document loads (measured by the review, R4). An entry is recomputed and says what it lost; a constraint on an entity that is gone makes the sketch itself invalid, which is why only that is refused.
    - A later feature that names an entity that went. As everywhere, a reference to what was removed is valid in a document: a projection of it keeps its last place with `brokenProjection` (measured), a region that names it is `noProfile`.
    - The tool and the app say what went and list the features that are not ok after the command.
- **`removeExternal` of an outline** takes the constraints on its entities with it, as the removal of any entry or own point does: the caller asked for the thing to go. An update is a change of the thing, and may not delete constraints nobody named.
- **`partial`**: a kind may say that `updateExternal` may leave fields out, which then keep what the entry has. An outline says it; `{ type: 'outline', regions: false }` switches the flag, `{ type: 'outline', curves }` is a revision. `addExternal` requires `curves`.
    - Only when the command's `type` is the type of the entry it updates; an update that changes the kind is the whole entry, as today (laid over an `edge` it would be a mix of two kinds).
    - The command's entry is checked for its fields, its `undefined` fields are dropped, and it is laid over `entryInput(sketch, id)` **before** the loop of `updateExternal` that keeps unchanged expressions (`document.ts`). A field left out then arrives as the expression the entry has, is found unchanged, and keeps its last value without being evaluated: an expression that is in error today stays, and does not fail the update (the review, agy 2; measured by the review, R6: expressions stay, also one whose parameter is gone, a number given drops its expression, the curves stay one object).
    - A field cannot be cleared by leaving it out. The two optional fields are cleared by a value: `name: ''` is no name, `readWith: null` none.
- **`updateExternal` validates an entry of an outline once.** Today it validates the form first and, when the value is not kept, the entry again with every reference (`document.ts`); for new curves that is two copies of the outline (the second round, fable 17 and agy 7). An entry that names nothing of the model (`refs` and `faces` of the shaped entry are empty) has nothing the second pass could check: the first is taken, with its fields.

### At the plug-in points of 6e

The names are 6e's ("Plug-in points" of its design); checked against `sketch-cut.ts`.

- **`sketchWorld`, `stepBase`, `toolBase`: nothing.** An outline's curves are reference curves of the base; `toolBase` takes them from `SketchResult.curves` with their flag, so a tool sees an outline closed as the recompute does.
- **`curvePredicates`: nothing.** `formsRegions` reads the flag; `mayCut` is false for what is not own; `holdsPoint` is true for a reference line, arc and circle and false for a spline.
- **`contactFix`**: a curve of an outline that forms regions is flagged as a projection of 6b is. The test becomes "a reference curve with `regions` whose entry is a projection from a sketch or an outline" (the entry of `o/l1` is `o`). With the ends of another curve the contact is not listed (6b's rule: the join of the own ends there cures it, and the position stage takes the outline's end in); any other contact is `fix: 'none'` with 6f's reason: "o/l1 is a curve of the imported outline o, which forms regions and is not cut: switch `regions` of o off … and draw the outline as own curves in a later sketch (the sketch tool projectSketch with as: "own"), then cut that; or remove the curve that meets it".
- **The flagged curve is asked for before the spline** (the review, agy 11, read in the code): today the function answers for a spline first, so a spline of an outline that an own curve crosses would get "move the other curve or the control points", which nobody can do to an import. A spline of an outline gets the outline's reason.
- **An extend** that would end on or cross such a curve is refused with 6e's text of a curve that forms regions and is not own, as for a projection; with the flag off an outline curve is a stop like a projected edge, and a `with` curve of a trim (measured). **A spline in its way is found by the shape of the curve**, not by `sketch.curves[C]` (`reachOf`, `extendSpec`), which knows own curves only: an extension toward a spline of an outline then says that a spline stops nothing, where today it would say that it meets nothing.
- **`namedOutside`** (the names a cut must not take) reads the texts of `external` through the references of each kind (`refs`), not by walking every entry: the curves of an outline hold no ID, and 2000 of them are not walked at every cut (the review, agy 13).
- **`readersOf`: nothing.** It answers for a cut of a tool; a revision is a command, and what it breaks is said by the recompute.
- **`repairsByDefault`: nothing.** A later sketch that projects a curve of an outline with the flag already counts (measured); a feature over a region of the outline's sketch already counts.

### With 6c, 6b and 6d

- **6c.** A line of an outline is an axis of a mirror and a direction, a point a centre (measured: a mirror about `o/l2`). A curve of an outline is no source of a pattern; 6c's text calls it "a projected circle", which stays. `openEndAdvice` gets the cure for an outline.
- **6b.** An entity of an outline is a source of a projection like any entity of an entry: `{ type: 'sketch', sketch: 'board', entity: 'pcbo/a1', kind: 'arc' }`, a point `pcbo/l1/a`, a control point `o/s1/1`. The whole-sketch form of `projectSketch` takes the curves of an outline (each in its role: with the flag when the outline has it) and none of its points; `as: 'own'` draws an own outline over an import, held on the projections (measured: 12 own curves, determined, following the revised file). `sketchSources` lists the entities with their places. One line: `isSplineOf` answers for a spline of an outline, so its projection is refused with 6d's text.
- **6d.** A spline of an outline is not projected, not cut, and no operand of a constraint, by the rules that hold for an own one; `projectSketch` leaves it out and lists it in `splines`. `get_sketch` and the query give it `through` and `box`.

### What consumers accept

6a's table, the row of an outline (the same as a projection from a sketch but for the source of a projection, which it is too):

| Consumer | An entity of an outline |
|---|---|
| A point of a curve of the sketch | no (a `coincident` joins to it) |
| An operand of a constraint of its sketch | a line, an arc, a circle and every point, with at least one own operand; a spline never |
| An operand of a generator (`sketchPoint`, a circle), an `AxisRef`, a frame of a placement | yes |
| A mirror axis, a direction or a centre of 6c | yes; not a source of a pattern |
| A point of a hole, a curve of a wall (`notProjected`) | no; the holes of a board are the regions of its circles, or a later sketch |
| `setCurvePoint`, the fillet's corner, a cut of 6e | no; a `with` curve of a cut of an own curve |
| A source of a projection of a later sketch | yes; a spline no |
| A region | with `regions: true` |

### Validation and the commands

- **The validator of the kind** (on `load`, `addFeature` of a sketch, `addExternal`, `updateExternal`): the fields (`onlyFields`); `curves` an object of 1 to 2000 entries; each key a local ID; each curve of its form; at most 2000 control points of splines together; the three numbers through `fields.number`; `anchor`; `regions`; `name` a text of the length of a name, an empty one stored as none; `readWith` by its form.
- **The rule of one curve is that it has an extent** (`curveProblem`): a line at least the length tolerance long; a radius at least the tolerance; an arc with its ends on one radius within the tolerance of an arc (1e-9 of its largest coordinate, and never more than 1e-7 mm), not a whole turn; a spline of 3 to 64 points whose control polygon is at least the tolerance long, closed only by its first point again (then at least 4), its ends otherwise not within the tolerance.
    - **Control points of a spline may stand at one place.** The first revision asked each to be the tolerance from the next. That refused what both readers give for ordinary files: a `C` with a node without a handle, an `S` or a `T` after a line, a DXF spline with a control point twice (all three reviews; six files in the review's probe). The engine has no such rule for an own spline and evaluates these.
    - **The tolerance of an arc is capped at a tenth of the join.** The placement puts the end of an arc on the circle of its start, which moves it by the difference of its two radii. With 6b's relative tolerance alone (1e-4 mm at coordinates of 1e5) the validator took an arc whose end the placement then moved out of its join: a ring 300 m from the origin of its file was welded, accepted, and no valid region (the third round, fable 1; L2). The cap costs nothing a reader gives: near the origin its arcs are within 1e-12, and 100 km away within the last bit of a coordinate, 1.5e-8 mm.
    - **What the import answers, the validator takes**: stated as a property and tested over generated files (K8: 400 paths with points on each other; L1 and L3: 2200 rings and 3000 files of curves at the scale of the join; none refused). The weld leaves out what has no extent before it closes anything, and its last step leaves out whatever `curveProblem` would refuse, so the property holds by construction and not by the care of each step.
- **The document never holds the caller's object, and its own cannot be written into.** The validator copies the curves once, freezes the copy (the record, each curve, each position) and remembers it (a `WeakSet`); an object it remembers is taken as it is, with no check, so every later validation of the entry (`fieldsOf` runs at every command of the sketch) costs nothing, and what is kept per object survives every command that does not change the curves. Frozen, because "remembered" means "checked": a caller that holds the document's object could otherwise write into it and send it back unchecked (the second round, fable 17). Measured (J8): the document holds a copy, and the same object after `addPoint` and after a switch of the flag.
- **`addExternal`, `updateExternal`, `removeExternal`** as they are, with `partial` and the rule above.
- **The text for an unknown type** lists the kinds; 6f adds `outline`.

### The import

`importOutline(format, bytes, options)` (`packages/engine/src/import/outline-formats.ts`), a function without a state, as `importMesh`:

1. The size of the bytes, before they are decoded; the options checked against the description of the format (`checkArgs`); the format reads the bytes into curves in millimetres, in the order of the file, each with its layer. **Its limits apply while it reads**, and are `tooLarge` at once, before anything is welded:
    - more than 8 million bytes (the server refuses by the size of the file, the bridge by the length of the base64 text before it is decoded, a reader by the length of its text);
    - more than 8000 curves from the layers asked for (four outlines' worth: the weld and the duplicates may bring a file under the limit of an outline);
    - more than 8000 control points in the spline curves it has made so far (a spline kept whole counts its control points, a Bezier piece its three or four);
    - more than 2000 control points in one DXF `SPLINE` (its conversion is quadratic: 2000 take 0.2 s, 8000 would take 4 s).
    - Measured (I8, I10, S9, S12): 9000 lines refused in 19 ms, five splines that make 9,940 control points in 92 ms, a path of 200,000 lines in 11 ms. The first revision named the limits of control points and enforced them in neither reader (the second round, all three).
2. **The local IDs**, from the curves as the reader gave them, by the kind of the file and its order. Nothing after this renames a curve.
3. **The weld** (below), which begins and ends by leaving out what has no extent and what lies on an earlier curve.
4. **`empty`** when no curve is left (the message lists the layers of the file and what was skipped); **`tooLarge`** above 2000 curves or 2000 control points of splines. Before anything is computed for the report.
5. **The report**: the unit and where it came from, the layers of the file with what each holds by type, what was skipped by reason, the curves by kind and the control points, the IDs (`ids`: the last number of each kind and the numbers not used, since a count of lines does not say their IDs once a number is unused; at most twenty of them, and beyond that `more` names the query `entryCurves`, which lists every ID once the outline is in a sketch; and `otherKind`, the IDs whose letter is not their type: a near-whole arc read as a circle is `a3`, so the circles are not `c1` to `c4` alone), what the weld did (`welded`, `moved`, `reshaped`, `reshapedArcs`, `bent`, `radius`, `closed`, `dropped`, `duplicates`, `blocked`, `crowded`), the ends that are open and the gaps (the nearest first; `atMost` on a distance whose search was cut short), the bounds, `readWith` (what the entry will store), and notes in words: the reader's own (a unit the file did not state, `$MEASUREMENT` 0 without `$INSUNITS`, entities off z = 0, two scales of an SVG), the gaps (with the weld that would close them only when the gap is beyond the weld: a gap inside it that was blocked needs another cure), what was blocked or crowded, **the arcs whose radius changed by more than the weld, each by its ID with the radius before and after** ("a3: 500 to 512; its centre moved with it": a caller then knows which centres not to build on), bounds under 1 mm or over 10 m ("is the unit right?"), more than 500 curves or 500 control points.

A format is a module of `import/` and a line of `OUTLINE_FORMATS`, described like an import format of D55 (`title`, `summary`, `extensions`, `options`, `read`), so the description for the AI, the tool and the app's file input read the catalog. Both formats take `layers`, `unit` and `weld`. The same bytes and options give the same curves under the same IDs.

**Not whole is refused; not read is listed** (the review, codex 5). A reader throws `unreadable`, with the place, for a file that is not a whole file of its format: a group code without its value, no `EOF`, a section or a polyline that does not end, an entity it reads without a group it needs, a number that is none; a tag that does not close or does not match, no `</svg>`, path data that does not parse. It never reads such a file as far as it goes: what is missing could be a hole, and the rest a plausible, wrong region. A complete entity of a type the reader does not take, or takes only in part, is left out and counted in `skipped` by its reason. The first design read a truncated SVG without a word.

### The weld

`weldOutline(curves, tolerance)`; the option `weld`, 0.01 mm unless given, 0 to 1. The first design merged every end within the tolerance of another, transitively, onto the first of them, and then moved the centre of every arc onto the bisector of its chord. All three reviews found it unbounded: a chain of close ends collapsed to one place (a corner drawn as 200 lines of 0.004 mm became a straight cut of 0.7 mm, a valid profile of the wrong shape), an arc of nearly a whole turn was dropped, and an arc of radius 1000 with a short chord came out with radius 912 when one end moved 0.009 mm. The first revision bounded it; the second round found what was left (an arc still moved beside a line, twins that kept an outline open, the IDs, the cost); the third found what the second rewrite brought in (arithmetic far from the origin, searches that were cut short and taken for an answer, a gap equal to the weld). This is the weld after all three.

0. **What is left out or closed whatever the tolerance.**
    - A curve with no extent is left out first (`dropped`): a line or a control polygon under 1e-6 mm, a radius under it whatever the sweep, a quadratic that returns to its start.
    - Then a curve whose own two ends are within 1e-6 mm is closed (`closed`): an arc of more than a half turn is a circle (one of less has no extent), a spline of four points or more ends on its first point exactly.
    - Both are asked again of what was closed, and a curve is counted once. The second revision closed before it asked for an extent, so with no weld an arc of three quarters of a turn and a radius of 4e-7 came out a circle the validator refuses (the third round, fable 6 and codex 4; L3).
    - **A curve that lies on an earlier one** is left out (`duplicates`): the same places within 1e-6 mm by distance, a line or a spline either way round; before the ends are looked at, because a twin makes every end of its curve met, and a square with four gaps and each side twice then stayed open (the second round, codex 5 and fable 6; K3).
1. **Curves that close onto themselves within the tolerance.** An arc of more than a half turn whose own two ends are within the tolerance, with no end of another curve near them, becomes a circle (a hole written as an arc from 0° to 359.9°); an open spline of four points or more likewise is closed onto its start. **A search that was cut short has not shown that no end is near**, and the curve is then left as it is: the second revision took an exhausted search for an empty one, so 65 unrelated lines that start 0.014 mm away made a circle of an arc that has a line between its ends (codex 3; L8). Otherwise the two ends of one curve are never welded to each other, and **an end never goes to the place its own other end stands at** (a line shorter than the gaps around it was collapsed and dropped: fable 8; K4).
2. **Met ends never move.** An end is met when an end of another curve is within 1e-6 mm of it, the tolerance of a join of the sketch. A file whose ends meet is not changed, however short its curves. (Asked in cells of the join, so a dense place does not cut that search short.)
3. **Open ends, in pairs, the nearest first**: an open end and an end of another curve within the tolerance. The partners of an open end are the open ends around it and, of the met ends around it, the nearest.
    - An end of a line or a spline goes onto the other end.
    - **An end of an arc goes only onto an end of another arc.** Of two open ends of arcs, the arc whose radius changes less in proportion gives way, then the later in the file: a deep arc beside a shallow one takes the move, and the shallow one keeps its radius (the third round, fable 4; L9). Beside a line or a spline the arc keeps the digits of its file: when the other end cannot come to it (it is met already, or it would go too far) the weld is not made. The first revision only preferred the line and let the arc move as a fallback: two lines that meet 0.005 mm from the start of an arc moved the arc's centre by 0.0035 with nothing reported (codex 4; K2).
    - An open end goes onto an end that is settled already only when that keeps it within the tolerance of where the file had it. So **no end moves further than the tolerance**, and nothing is merged along a chain.
    - **Equal is within, wherever the file stands.** "Within the tolerance" has a slack of 1e-9 mm, a thousandth of the join, and the pairs are ordered by their distance in that unit, then by the order of the file. Without it a gap of one unit of the last digit of a file of two decimals, which is the default weld, closed at 214 of 400 places (`4.86 − 4.85` is more than 0.01 in doubles), and three ends with equal gaps were paired by rounding (fable 5; L6).
4. **An arc that gives way to another arc is the circle through its two ends and the middle of the arc of the file**, computed relative to one of the three points. The move is made only when all of these hold; otherwise the end stays open and is counted in `blocked`:
    - the three points are not nearly in one line: the middle more than 1e-6 mm off the chord, and the radius at most a million chords (the second revision stopped only at 1e-12 of the size squared, where the two ends are off one radius by the arithmetic alone: fable 4);
    - the arc it gives is one the validator takes, its two ends on one radius (checked on the arc itself, before the weld is made: codex 5);
    - the middle lies between the new ends the same way round (the arc keeps its branch, the short or the long way);
    - **the whole arc of the file is within the tolerance of the new circle.** The distance from a point of the old arc to the new centre has its extremes at the ends of the arc and where the arc passes the line through the two centres; those places are computed and checked, so the bound is of the arc and not of samples. The second revision checked the two quarter points: an arc of 300° passed with its ends, middle and quarter points within the weld and a place at 15 % of its sweep 0.0115 mm off (codex 6; L8).
    - An arc whose ends stayed is the arc of the file, to the digit: it is not touched (the first revision put its centre on the bisector again whenever its ends were off one radius by more than rounding: agy 3).
    - **Relative to one of its points**, because the circle through three points computed from squared coordinates of the file loses its digits as the square of the distance from the origin: 300 m away the two ends of the new arc were 1e-5 mm off one radius, the validator of that revision took it, and the sketch was no valid region (fable 1). Now 5e-8 at 500 km, which is the last bit of the centre's own coordinates (L2).
    - **The centre and the radius are not bounded, and the report names the arcs.** A bound on the centre is ill-conditioned for a shallow arc: an end moved by δ across the chord moves the centre by about δ · R / chord, though the arc moves by δ, so two arcs of radius 500 over 2° written with three decimals stayed apart in 80 of 200 placements under the first revision's bound (fable 7 of the second round). Bounded by where the arc runs, every such joint of three and four decimals closes (K11, L9). **What the radius then is, is not "what the digits leave open" but unbounded once the sagitta of the arc is near the weld**: with three decimals a radius of 500 over 2° changes by up to 3.8 mm (0.8 %), of 100 over 1° by 14 %, of 2000 over 0.2° by 22 %; pulled towards its chord, an arc of radius 500 over half a degree came out with a radius of 512,934 (L9). The arc is still where the file drew it, within the weld. The report gives the largest change (`radius`), every such arc with its radius before and after (`reshapedArcs`, at most twenty), and a note that names them when the change is over the weld. A numeric bound on the radius would only leave open what the digits of the file cannot decide (the third review's answer to the question put to it, on these conditions).
    - agy's finding that the sweep could flip to its complement under the first revision's test did not hold for that test (the nearest point of the bisector does not cross to the mirror image while the centre moves by no more than the tolerance) and is moot with this one, which asks where the middle lies.
5. **Step 0 again**, for what the weld made: a line whose two ends are one place, a curve that now lies on another. **And, as the last thing, whatever the validator of the kind would refuse is left out** (`dropped`): the property "what the import answers, the validator takes" is then true by construction (codex 4).
6. **The report says what happened**: `moved` is the furthest any end went from its place in the file, at most the tolerance; `reshaped`, `reshapedArcs`, `bent` and `radius` are of the arcs that gave way, `bent` the furthest the arc of the file lies off its new circle over its whole length; `closed`, `dropped` and `duplicates` are the changes of what the outline consists of; `blocked` counts the open ends that had an end within the tolerance and are still open, `crowded` those the weld left alone; `gaps` lists them.

**The cost is bounded, and a bound that is reached is never an answer** (the second round, codex 7 and fable 3; the third, codex 2 and 3, fable 2, 3 and 11).

- **Every search for ends** is in the nine cells around a place and looks at no more than 64 candidates, **whatever they are**: the count is of what was looked at, before any test. The second revision counted only the candidates its test accepted, so the bound did not bound: 2000 circles about one centre were 3,998,000 comparisons.
- **A search that was cut short says so, and its caller treats it as unknown**: the curve is not closed onto itself (step 1), the end is `crowded` and left alone (step 3), the distance of a gap is an upper bound (`atMost`).
- **A crowd is of open ends**: an open end with more than 8 other *open* ends within the tolerance is `crowded` and is not welded, so there are at most 9 pairs per end (8000 lines whose ends lie in two clusters made 64 million pairs in the first revision, and are 800 crowded ends in 15 ms now, K6). The met ends around an end are no crowd: counted with them, the end of a polyline of short segments was left alone, and the line that should have started there was welded to the vertex before it, a T with an open end that no larger weld closed (fable 3; L5). Of the met ends only the nearest is a partner, which keeps the bound of pairs.
- **A twin is looked for among the curves that share all that places it**, a step at a time: a line by one end and then the other, a circle by its centre and then its radius, an arc by its start, its end and then its centre, a spline by its count, its two ends and then the mean of its control points; each step in the cells around. Curves that share one point only are never compared: 8000 lines from one point are 3 comparisons a curve and 145 ms (4.6 s before), 8000 circles about one centre none (L7). `outlineRevision` uses the same index.
- **The gaps of the report are found outward**: the nearest other end is looked for in cells of one tolerance, then of ten, then of a hundred, and the first size that has one gives it. The second revision searched cells of a hundred tolerances with the bound of 64 candidates, and a contour's one gap of 0.015 mm was not listed when 64 strokes lay within a millimetre of it (fable 2; L4). After the limits of an outline are checked: 2000 strokes that do not meet take 65 ms, where the first revision took 14.5 s (a walk over 40,000 cells per open end).

**A file welds the same wherever it stands** (L1: 2200 generated rings, each at three places, the same counts, the same curves and the same ends within 1e-7 mm). It follows from three things above: the circle computed relative to one of its points, the slack, and pairs ordered by a rounded distance. It does not hold where a search is cut short (the cells fall elsewhere) nor beyond some kilometres from the origin, where the last bit of a coordinate is over the slack ("Known limits").

With a tolerance under 1e-6 mm only steps 0 and 5 run. The default stays 0.01 mm: it closes files down to two decimals of a millimetre where lines meet arcs (A3); two arcs that meet need three (K11: with two, an angle rounded to a hundredth of a degree is 0.09 mm at a radius of 500, beyond the weld, and the report lists the gap).

### The readers: DXF

ASCII DXF, any release. Read by hand (`import/dxf.ts`); the text is decoded as UTF-8, a byte-order mark passed over.

- **Groups**: a code line and a value line, both trimmed; CR LF, LF or CR; read up to the group `0`, `EOF`, and nothing after it. A comment (group 999) is passed over wherever it stands, so it does not come between `0 SECTION` and its name or `$INSUNITS` and its value (the second round, agy 12). `unreadable`, with the line: a code that is not a whole number, a code without its value, a number that is empty, none or not finite (never read as 0), a file with no `EOF` ("the file is cut short"). The sentinel of a binary DXF and the head of a DWG are `unreadable` with what to do ("save it as ASCII DXF").
- **Sections**: `HEADER` for `$INSUNITS` and `$MEASUREMENT`; `ENTITIES`. `BLOCKS`, `TABLES`, `OBJECTS` are passed over. A `SECTION` without `ENDSEC` is `unreadable`. A file without any `SECTION` that is a bare list of entities up to `EOF` is read as its entities.
- **Units**: the option `unit` (`mm`, `cm`, `m`, `in`, `ft`, `mil`, `um`, `dm`); else `$INSUNITS` 1 in, 2 ft, 4 mm, 5 cm, 6 m, 8 microinches, 9 mils, 10 yards, 13 microns, 14 decimetres; 0 or no header is millimetres, and the report notes it, with the advice to give `unit: 'in'` when the header says `$MEASUREMENT` 0 (imperial) and no unit; any other value is `unreadable` with "give the option unit" (the first design had no option for microns and decimetres, a dead end: the review, fable 17).
- **Layers**: group 8 of each entity (`0` without one); the option `layers` by exact name. The report lists every layer. **The counters and every table looked up by text of the file have no prototype** (a `Map`, or an object made by `Object.create(null)`): a layer named `__proto__` is a layer like any other, and nothing a file names is read from or written to `Object.prototype`. The second revision's nested counters on plain objects let `<g id="__proto__"><circle/></g>` set `Object.prototype.circle` for the rest of the process (the third round, codex 1; L10). The same holds for the SVG reader's counters, its attributes, its entities and its units, and for the option `unit`.
- **`LINE`** (10, 20; 11, 21); **`CIRCLE`** (10, 20, 40); **`ARC`** (10, 20, 40, 50, 51: degrees, counter-clockwise from 50 to 51; equal angles, or a whole turn apart within 1e-9°, are a circle; an arc that only nearly closes is the weld's). An entity without a group it needs is `unreadable`, with its type and its line.
- **`LWPOLYLINE`** (70 bit 1 closed; per vertex 10, 20 and the bulge 42) and **`POLYLINE`** with its `VERTEX` entities up to `SEQEND` (the form the engine writes; without `SEQEND`, or a `VERTEX` outside a polyline: `unreadable`): a segment per pair of vertices, a line, or with a bulge `b` the arc that turns by `4 · atan(b)`, counter-clockwise for a positive bulge; its centre is `(p + q) / 2 + ((1 − b²) / (4b)) · perp(q − p)`. Vertices at one place make no segment. **A count the file declares is checked against what was read**: the vertices of an `LWPOLYLINE` (group 90); a polyline that declares four and holds three was read as a triangle (the second round, codex 8), and is `unreadable` now with both numbers. A missing count is no error (old writers). A `POLYLINE` fitted to a curve or a spline (70 bits 2, 4) is read by its curve vertices: the vertices of its frame (vertex flag 16) are passed over, or the frame would be read as lines. A `POLYLINE` that is 3D or a mesh (70 bits 8, 16, 32, 64) is left out and listed. Widths are not read.
- **`SPLINE`**, checked before it is converted (`bsplineBeziers` checks neither the order of the knots nor that they are clamped: given knots out of order it answers with four pieces and no word, I6; the reviews, codex 6 and agy 4):
    - `unreadable`: knots or control points that are no numbers, a count of knots that is not the control points plus the degree plus one, knots out of order, a declared count of knots, control points or fit points (72, 73, 74) that is not what was read.
    - Left out and listed, each by its reason: rational (70 bit 4, or weights that differ), a degree outside 1 to 3, fit points without control points, periodic or not clamped at both ends, no extent, a break in the curve (an inner knot repeated more than the degree).
    - Knots within 1e-9 of their span are one knot, so knots that differ in the last digits give no piece without extent. A piece that has none all the same is given to the weld, which leaves it out with every other such curve, after the IDs.
    - More than 2000 control points in one `SPLINE` is `tooLarge`, before it is converted.
    - **A cubic with even, clamped knots and 4 to 64 control points is one spline of the sketch** over those control points, and a quadratic of 3 points likewise: 6d's spline is that curve (measured, I6b: 0 mm from the Bezier pieces of the file), so a free-form side of five spans is one entity and one face, not five (the review, fable 9).
    - **Any other is its Bezier pieces**, exactly (`bsplineBeziers` of 6d): a line per piece for degree 1, a spline of three control points for degree 2, of four for degree 3; the pieces share their ends to the digit. Over the same control points a spline of the sketch would be another curve (I6b: 0.88 mm off). Each piece is a curve of the limits.
- **The extrusion direction** (210, 220, 230; by default (0, 0, 1)). `CIRCLE`, `ARC`, `LWPOLYLINE` and a 2D `POLYLINE` (by the groups of its header) are in the coordinates of their own plane: with 230 negative their x is mirrored, an arc's angles and a bulge's sign with it; with a direction that is not along z they are left out and listed ("(tilted extrusion)"). `LINE` and `SPLINE` are in world coordinates: they are never mirrored and a 210 group on them changes nothing (the reviews, fable 17 and agy 3: the prototype did not mirror a 2D `POLYLINE`, which tears an outline drawn from below apart; measured after, I3). A z is not read; the report notes a file whose entities do not lie at z = 0.
- **Paper space**: an entity with 67 = 1 is left out and listed ("CIRCLE (paper space)"), a `POLYLINE` with its vertices, before anything else is asked of it; the first revision's text said so and its reader did not (codex 11: a circle of a layout became a hole). It counts in the layers of the report and not in the limits.
- **Left out and listed** (`skipped`, by type with a count): `INSERT` (blocks), `ELLIPSE`, `TEXT`, `MTEXT`, `DIMENSION`, `HATCH`, `POINT`, and every other type.

### The readers: SVG

SVG 1.1, the subset of the plan (`import/svg.ts`), as text in UTF-8. The prototype's first reader split tags by a pattern and path data on letters; the review (codex 7, agy 5) found it read `1e1` as a command `E`, misread arc flags written without separators, and divided by zero for an arc with equal ends. It is a tokenizer now, of the document and of path data (450 lines in the prototype).

- **XML**: a scanner with a stack of open elements. Elements and attributes (either quote), comments, processing instructions, CDATA and a `DOCTYPE` without declarations of its own are passed over; the five predefined entities and numeric ones in attribute values. Prefixes are read as written (`inkscape:label`); an `svg:` prefix on an element is dropped. `unreadable`, with the character: a `<` that starts no complete tag, a closing tag that does not match the open element, elements still open at the end (no `</svg>`), an attribute without a quoted value, **an attribute twice on one element**, an unknown entity, a `DOCTYPE` with an internal subset, no `svg` element, **anything but white space, comments and instructions outside the one root** (a second `<svg>` was dropped without a word: the second round, codex 9).
- **Numbers are finite**: `1e999` in a length, in path data, in `points`, in a `viewBox` or in a transform is `unreadable` with the place, and so is a coordinate that is not finite after the transforms.
- **Millimetres**: the option `unit` (what one user unit is); else `width`, `height` (mm, cm, in, pt, pc, px or none; positive) over the `viewBox`; a root without them at 96 units per inch, with a note. **Of two scales that differ the one a viewer takes is taken**: the smaller (`meet`, the default), and the larger when `preserveAspectRatio` says `slice` (the third round, fable 12; L10); without a word within 1e-6, with a note that names both otherwise; only `preserveAspectRatio="none"` with scales more than a thousandth apart is `unreadable` ("give the option unit"). The first revision refused any difference over 1e-6, and with it an A4 page whose `viewBox` an optimiser had rounded to two decimals (the second round, fable 16; S11). The origin of the `viewBox` moves nothing: the coordinates are the user space of the root.
- **A length of a shape with a unit** (`r="10mm"`, `x="1in"`; mm, cm, in, pt, pc, px) is user units at 96 per inch, as SVG says: 10 mm in a drawing whose user unit is a px, and 37.8 units in one whose `viewBox` makes a unit a millimetre (measured, S4). With `%`, `em` or `ex` the shape is left out and listed ("circle (length in %)"); a value that is no number is `unreadable`.
- **y points down in SVG**: every place is read as (x, −y), so the drawing looks as it does on the screen, below the x axis. (The engine's writer wrote (u, −v), so its own files come back where they were.)
- **Layers**: the groups an element is in, each by its `inkscape:label` or else its `id`; the option `layers` takes an element when one of its groups is named.
- **`transform`** on a group or a shape: `translate`, `rotate` (with a centre too), `scale`, `skewX`, `skewY`, `matrix`, composed down the tree; any other name is `unreadable`. Lines and splines take any transform that has an inverse; under one that has none (`scale(2,0)`) a shape is left out and listed ("(flat transform)"). A circle or an arc under a total transform that is not a similarity (its two columns of one length and perpendicular, within 1e-9) would be an ellipse: its shape or its whole path is left out and listed ("(uneven transform)"). A reflection is a similarity: an arc under it runs the other way, and its ends swap (measured, S8).
- **`path`**: a scanner of command letters and numbers (a sign, a fraction without a leading digit, an exponent; no separator where the grammar needs none; the two flags of an arc one character each). It is lazy: a segment at a time, so the limits of curves and of control points end a huge path where they are reached (S12). `M`, `L`, `H`, `V`, `Z`, `C`, `S`, `Q`, `T`, `A` and their relative forms, the arguments counted, a repeated group an implied command. `C` and `S` are a spline of four control points, `Q` and `T` of three; the smooth forms reflect the control point before. An arc by SVG 1.1, F.6: equal ends are no segment, a radius of 0 a line, a radius under half the chord raised to it, then the centre from the two flags. Path data that does not parse (a number that is none, a count of arguments that is wrong, a flag that is not 0 or 1, a letter that is no command, no `M` first) makes the file `unreadable`, naming the path and the character. A well-formed path with an arc of two radii is left out whole and listed.
- **`rect`** (with `rx` equal to `ry`, or one of them given, the corners as arcs; two different: listed), **`circle`**, **`ellipse`** with equal radii (a circle; with two: listed), **`line`**, **`polyline`**, **`polygon`**.
- **Passed over with their content**: `defs`, `clipPath`, `mask`, `symbol`, `pattern`, `marker`, `metadata`, `style`. **Left out and listed**: `text`, `image`, `use`, a nested `svg`.
- **Not read**: CSS (`style`, classes, a transform in a style), fills and strokes (a filled shape is its outline), `display` (a hidden element is read).

### The query `entryCurves`

An entry of `QUERIES` (`query/entry-curves.ts`): the curves of one entry of a sketch with their places, a page at a time, for any kind of entry (the copies of a pattern too, which 6c lists short).

- **Arguments**: `sketch`, `entry`, `kind` (optional: `line`, `arc`, `circle`, `spline`), `from` (how many to pass over, default 0), `max` (default 100, at most 500).
- **Answer**: `status` (`ok`; `unavailable` when the sketch did not evaluate; `noEntry`), `total`, `from`, and `curves`, each with its ID, its flag `regions` and its place in the sketch rounded as positions are: a line by `a` and `b`, a circle by `center` and `radius`, an arc by `center`, `start`, `end` and `sweep`, a spline by `through` and `box` (6d's), by `closed`, and by **`control`, its control points in order** (`<id>/<i>` stands at `control[i]`). The control points of a spline of an outline may be constrained to and projected, and the points it runs through are not them; the first design gave no bounded way to read where they stand (the review, codex 13).
- **A page is bounded by positions as well as by curves** (the second round, fable 11): it ends when its curves hold 2500 positions together, but never before its first curve. A spline of 64 control points is 64 positions and about 120 more of `through`; 500 such in a page would be 2 million characters.
- It reads the state of the solved sketch (`context.sketch`), no body (`geometry: 'none'`). It costs its line in `QUERIES` and its rows in the two typed tables of `packages/mcp/test/queries.test.ts`; the app reaches it through the generic form.

### The query `sketchRegions`

An entry of `QUERIES` (`query/sketch-regions.ts`): the regions of a sketch with their whole references, a page at a time.

- **Why.** A command names a region by its whole sorted outer loop (`RegionRef { outerLoop }`), and there is no other form. `get_sketch` is the only place a loop leaves the server, and the first revision capped it at 20 IDs, pointing to "the query `regions`", which does not exist. So a region of more than 20 curves, which is what an imported outline mostly is, could not be extruded through MCP at all: the design's own cases A2 (67 lines), H5 (the lid's section) and the outline of 500 lines were beyond it (the second round, all three reviews, serious).
- **Arguments**: `sketch`; `curve` (optional: only the regions that this curve bounds, by its outer loop or a hole: the way from `board/l1` to the region to extrude); `index` (optional: only the region at this place among the regions of the sketch); `holes` (a flag: list the loops of the holes too); `from`; `max` (default 20, at most 100).
- **Answer**: `status` (`ok`; `unavailable`; `invalid` when the profile is, and then no region), `total`, `from`, and `regions`, each with its `index`, its `ref` whole, as a command takes it, its `area`, its `box`, the count of its `holes`, and with the flag `holeLoops`, each by the IDs of its curves.
- **`index`, `from` and `total`, each said once** (the third round, fable 9).
    - `index` is the place of the region among `SketchResult.regions`, whatever the filter and the page.
    - `from` counts, and `total` is the count of, the regions that match (`curve`, `index`), in their order in the sketch.
    - The rows of `get_sketch` are grouped by copies and capped, so the place of a row there is not the index of its region: a capped row carries the `index`, and names the call `sketchRegions { sketch, index }`, as the row of an outline names `entryCurves`.
- **The holes are counted, and listed only when asked for.** No command needs them (a region is named by its outer loop), and a plate with 1900 holes would answer 1900 IDs for a reference of four.
- **A page ends at 2000 IDs**, outer loops, and holes when they are listed, but never before its first region: a region is never cut, however long its loop (the outer loop of an outline of 2000 lines is 14,000 characters, which a command that names it has to carry anyway).
- **Where it reads.** The outer loop, the area and the box from the result of the sketch (`SketchResult.regions`). The IDs of the holes, and the filter by a curve of a hole, from the kept profile of the sketch (`context.sketch(sketch).profile.regions[i].holes[j].curves`, one ID per edge, made unique), which the query `sketchContacts` reads already: the result holds the loops as polylines without IDs, so the second revision's "it reads `SketchResult.regions`" could not have given them. No type of the result changes; no body is read.
- For every sketch, not for outlines alone: a mirrored outline of 6c or a polygon of a hundred sides has the same long loop.
- Its line in `QUERIES`, its rows in the two typed tables; in point 5 of the work.

### The step, in order

1. `resolveReferences`: an outline's value from its entry (never lost); its geometry; for a kind with `narrow`, `solver`, the part the constraints name.
2. `solverSetup` (reading `solver` where there is one) and the solver, as today; in the adapter, two fixed points at one place are one end.
3. The geometry after the solver, on each of its three paths, with the points and the radii of the entries the solver did not get, in one order.
4. `sketchWorld(stepBase(…))`: the curves of the outline among the reference curves, 6c's position stage over them when the flag is on, a closed curve without an open end.
5. The profile, the result (the curves of the entry with the flag, `openEnds`).

## The document and the schema

- **What the document gains**: an entry `{ type: 'outline', … }` in `external` of a sketch, with its curves, and its value `{ kind: 'outline', … }` in `solved.external`. Region references and face names hold the IDs of its curves, strings to every build.
- **No upgrade step, no new version; `SCHEMA_PENDING` stays 0 and the version 10.** A build without the kind refuses the entry (`externalRef`, with the text that lists the kinds it knows), so a document with an outline is an invalid document there, not a model with the outline dropped; its stored value belongs to the entry and goes with it. This is the rule of `schema.ts` ("no step is needed where a build without the addition refuses by itself") and what 6a said of 6b, 6c and 6f. The plan expected a step for a section; there is no section.

## MCP

- **The tool `import_outline`** (`ImportOutlineArgs`, `ImportOutlineAnswer` of the contract), in `server.ts` beside `import_mesh`, since it reads a disk.
    - **The route** (the second round, agy 8). The server reads the bytes, refuses by their size, and hands them with the arguments to one function of `tools.ts`, `outlineInto`, which runs where the engine is: on the server's own engine, or in the app over the bridge as the internal tool `_outline`, as `_load` carries a document. There the file is read (`importOutline` is engine code) and the command sent. So a replacement reads the entry's `readWith` from the document it is about to change, with no question across the bridge; both routes give one answer; and the revision is computed from the document, not from an answer of `get_sketch` or `get_document`, which leave curves out. The first revision read the file on the server and did not say how the stored options reached it.
    - **Two steps, so that the question can be asked before the call** (the third round, fable 8 and codex 7). `outlineInto` is `prepareOutline`, which changes nothing (it resolves the options, reads the file and makes the command), and then `execute` of that command. The app asks `changesDocument` in `beforeCall`, before any answer exists; the second revision gave that function the answer of the call, which it cannot have.
    - **For the app**: `_outline` is in `MUTATING`. `changesDocument` answers for it as it does for `sketch_tool`: false without `sketch`; otherwise it prepares the command and asks its own preview of it, and false when the preparation is refused. So a look at a file, a file that cannot be read and a replacement the rule of an update refuses do not end a draft of the user. The file is then read twice, and only while a draft is open (the app asks that first).
    - **A refused command comes back inside an answer that is `ok`**, because it carries the report. The status line of the app therefore reads the answer (`outlineSaid`), not the outcome alone: nothing for a look, as for a query; that an outline was imported, with the entry and the sketch, when the answer has `entry`; the refusal as an error when it has `refused`.
    - **The file crosses the bridge as base64** (`{ file: { name, base64 }, … }`, the envelope `tools.ts` has for exported files): the arguments of a bridged call are JSON, and a `Uint8Array` does not survive `JSON.stringify` (codex 8). The limit of a file is one number, 8 million bytes, checked three times: by the server on the size of the file, by `outlineBytes` on the length of the text before it decodes anything, and by a reader on its text.
    - Without `sketch`: the report only. An AI looks at a file first (its layers, its size, its unit) and then places it. `replace` or `remove` without `sketch` is refused.
    - With `sketch`: `addExternal` under `id` (by default the name of the file reduced to an ID, numbered while taken), with `x`, `y`, `turn`, `anchor`, `regions` as given and `readWith` as the file was read. One undo step.
    - With `replace`: `id` is required.
        - The format is what the extension of the path names, and the entry's when it names none (a board saved as SVG in the place of a DXF is read as SVG: the first revision took the stored format and would have refused it at its first line; fable 13).
        - The options: those given, whole. When `options` is left out and the format is the entry's, those the entry stores, so the revised file is read as the first was (the scenario's board: the layer `Edge.Cuts`, with no option given). `options: {}` reads every layer with the defaults, which is how a stored choice of layers is given up. The stored options of another format are not used (`unit: 'mil'` is no option of SVG), and `next` says so.
        - Then `updateExternal` of the entry with the new curves and the new `readWith`, and the fields given; the answer has `revision`.
    - With `remove`, a list of constraints of the sketch: they are removed in the same batch, before the update. This is the way past the rule of an update through MCP, in one undo step: a replacement that is refused changes nothing and leaves the constraints, its message names them, and the caller repeats the call with `remove` (the reviews, codex 9 and fable 6).
    - The answer: the report, also when the command was refused (`refused`, its message); the entry; the brief of the sketch after the command (status, valid, regions, open ends) and the features that are not ok (a mirror that lost its axis, a projection that lost its entity); `next` in words. How the entities are named is in the report (`ids`: the last number of each kind, the numbers not used, the IDs whose letter is not their type, and the query to ask when the list of unused numbers is cut; the first revision gave counts, which stopped naming the IDs once a number can be unused: fable 14). Never the curves.
- **`get_sketch`** gives an outline its own row (`OutlineDetail`): the fields with their expressions, **what it was read with** (`readWith`; the row's own `source` is the word for the kind of an entry, reference or derived, which is why the entry's field is not called so: fable 15), the counts by kind, the box as placed, the first curves at their places, `listed` and `total`, and with more curves the query that gives the rest. The points of an outline are not listed apart: each curve says where its points are, and their IDs follow from the curve's.
    - **The curves listed are bounded by positions too**: at most 50 curves holding at most 500 positions together (the first whatever it holds), and a spline without `through` (the query gives it). The first revision's bound of 50 curves is 4000 characters for lines and 140,000 for 31 splines of 64 control points (fable 11).
- **The rows `regions` of `get_sketch` are capped** (`regionRows`; the review, fable 4: 33,841 characters for 1000 curves): at most 50 rows and the count of the rest; an outer loop of more than 20 IDs is printed as its count, its first 20 IDs, the entries they are under, its `index` among the regions of the sketch, and **the call of `sketchRegions` that gives it whole** (by that `index`).
- **The queries `entryCurves` and `sketchRegions`** through the tool `query`, as every query. With the second, a region of any length is extruded from the answers of MCP alone (`calls.ts`, `regionThroughMcp`: the outline of 500 lines).
- **`get_document`** prints the text of `OUTLINE_OMITTED` in the place of the curves of an outline above 50 on each of its paths: the whole document (`documentShown`), one feature (`get_document { feature }`, which returns the feature as it is today: 72,666 characters measured by the review), and a feature of a stored document. One helper for the three. `save_document` writes the curves. (agy read the whole curves in `get_document` as acceptable for a tool that shows the raw document; the other two reviews and the tool's own treatment of a stored mesh say otherwise, and an answer of 140,000 characters is of no use to its reader.)
- **`describe_api`**: `SketchOutline`, `ImportedCurve` and `OutlineReadWith` from `types.ts`; the kind in the generated section "Entries of a sketch" by its `summary` and its `example` (a small outline written out, accepted by the test of the examples); a generated section "Outline formats" from `OUTLINE_FORMATS` (per format its summary and its options), as "Import formats" is generated; in the paragraph on reference geometry one sentence: an outline is placed by its fields, its entities are `<entry>/<local>`, and a revision keeps IDs by kind and order.
- **The advice of `get_sketch`** for open ends of an outline: `OUTLINE_OPEN_END`.

## Issue codes

None new. An outline has no warning of the recompute (it cannot fail). What a revision breaks is said by the codes that exist: `brokenProjection` with 6b's detail ("board has no circle o/c4"), `brokenCopies` for a mirror or pattern that named an entity that went, `noProfile`, `brokenReference`. The refusals of an import are codes of its own outcome (`invalidArguments`, `unreadable`, `empty`, `tooLarge`), as those of `importMesh` are.

## Rejected alternatives

- **A section `outlines` of the document** with `addOutline` and `removeOutline`, as `meshes`. "The stored outline: in its entry"; Open, 1.
- **The curves as own geometry tied by `fixed`** (the plan rejected it for the cost of the analysis). The stronger reasons: 3000 own points in the solver (the memory, C4), nothing to revise as a whole, and the IDs of a file among the IDs of the sketch.
- **One entry per curve of the file.** 2000 entries, each validated, resolved and stamped apart, and a revision of 2000 commands.
- **Points shared between curves, with IDs of their own** (6a's first vocabulary). The numbering of vertices shifts with every vertex a revision adds, a vertex has no name a person can find, and the joins by position make sharing unnecessary.
- **IDs from the geometry** (a hash of a rounded position, so that an entity that did not move keeps its ID whatever the order). A board made wider would rename every entity that moved, which is the case the scenario asks to survive; and two revisions rounded apart by a digit would differ. The plan defers matching by geometry.
- **IDs from the handles of a DXF** (group 5). Stable in some tools and renumbered at every export in others; SVG has `id` only where an author wrote one. Not a rule a caller can rely on; a later option of the reader, not excluded.
- **The value as positions** (the forms of 6b, one per entity, or one large form). The document would hold every coordinate twice and the stamp would hash them at every solve.
- **The whole outline in the solver's input** (as every reference today). Measured: aborts.
- **The narrowing for every kind.** It would change the stamp of every stored sketch with a projection for nothing: their entries are a handful of points.
- **The flag per curve** (some curves of an outline bound regions, some do not). The choice of layers at the import and a second entry do it without a field per curve.
- **A placement on a point of the sketch or of reference geometry** (the plan's amendment allows the second). "The placement".
- **A mirrored placement or a scale.** The readers settle the unit; a mirror is a second field for a case no scenario has (a board seen from below is mirrored by its file's extrusion direction, which the reader reads).
- **The readers as entries of `IMPORT_FORMATS`.** Its type and every consumer of it mean a mesh.
- **`import_outline` answering with the batch** (the plan). Open, 2.
- **`get_sketch` with every curve, or with none.** 79,000 characters for 1000 curves; with none an AI could not constrain to anything without a second call even for a board of twelve curves.
- **A weld inside the sketch** (the position stage with a larger tolerance for outlines). Two tolerances of "the same place" in one profile; and the arcs would stay off their radius.
- **A weld that merges every end within the tolerance, transitively** (the first design). Unbounded: an end at the far side of a chain moves by the length of the chain, and a finely drawn corner collapses into a valid profile of another shape (the reviews; J1, J2).
- **A transitive weld with a refusal when an end moved further than the tolerance.** It would refuse the file of J1, which needs no weld at all. Leaving met ends alone removes the case.
- **Every arc re-centred onto the bisector of its chord** (the first design). Ill-conditioned for a short chord under a large radius (radius 1000 became 912). Arcs keep their file's centre; one is moved only where two arcs meet, within the tolerance.
- **Welding by moving both ends to their middle.** One end keeps its digits, so a file that needs no weld is not changed at all; and an arc would have to be re-centred at every corner.
- **No weld, a refusal with advice.** The files that need it are ordinary (four decimals), and the cure is not in the caller's hands.
- **A reader that reads a broken file as far as it goes** (the first design, for SVG). What is missing could be a hole.
- **The IDs given after the weld** (the first design). A curve dropped in one revision would rename every later curve of its kind, and the IDs would depend on the weld.
- **The options of an import not stored** (the first design). A replacement read another outline than the one it replaced.
- **The outline's value as a fifth form of `Projected`** (the first design). The code of 6b would hold a form it can never have.
- **The validator keeping the caller's object when it is canonical** (the first design). The caller could write into the document, and the check cost two serialisations at every command of the sketch.
- **A constrained entity released silently by a replacement.** An update may not delete what nobody named; the caller names the constraints (`remove`), or keeps the curve.
- **A numeric scale as the unit option** (the review offered it beside more unit names). The names cover what `$INSUNITS` can say; a factor invites a second, silent way to get a size wrong.
- **A periodic spline clamped by the reader.** Exact, by the review's probe; not written for the first version, listed and in the backlog.
- **An arc that gives way to a line when the line cannot move** (the first revision). The arc was re-centred with nothing reported. An arc gives way to an arc only.
- **A bound on the centre and the radius of an arc that gives way** (the first revision). Ill-conditioned for a shallow arc, which then stayed apart; the bound is on where the arc runs.
- **The radius kept and the joint left open when it would change by more than the weld.** The outline would not close for a file whose digits do not hold the radius anyway; the arc of the file is within the weld of the new one, and the change is reported.
- **A near-whole arc numbered among the circles** (the first revision), or the closing done by the reader with a tolerance of its own so that the IDs follow the kinds. The first made the IDs depend on the weld; the second would need a second tolerance that means "closed" beside the weld. The ID is the file's, the type is the curve's.
- **Every pair of ends within the weld collected, however many** (the first revision). 64 million pairs for a file under the limits. A crowded end is left alone.
- **Each control point of a spline at least the tolerance from the next** (the first revision). It refused ordinary files.
- **The whole loops kept in the fifty rows of `get_sketch`** in the place of a query (agy's alternative). An outer loop of 2000 IDs is 14,000 characters in an answer that is read for other things, and the fifty-first region still needs a way.
- **The stored options asked across the bridge before the file is read** (a call for the entry, then the import on the server). Two calls and a state between them; the file goes to the engine instead.
- **The options of a replacement merged field by field with the stored ones.** A stored choice of layers could then not be given up (a list has at least one name); given options replace the stored whole.
- **Two fixed points within 1e-6 mm as one end, whatever the size of the arc** (the first revision). Right for a board; for an arc of radius 1e-4 it takes a point through which no tangent passes.
- **A chain of two coincidents read as a common end.** It would change decisions for sketches without an outline; D52 left it out, and so does this.
- **A library for DXF or SVG.** The plan says by hand; the subset is small (the two prototype readers are a few hundred lines each), and a library needs the owner's approval and a port.

## Known limits

- **IDs follow the order of the file.** A file whose tool lists entities in another order after an edit renames them: what named `c1` names another hole (B6). A curve that did not move and has another ID is told (`renamed`, J11, K10); a curve that moved and changed its place in the file at once is only `changed`, and "kept" means that the ID still exists, not that it is the same feature of the drawing. The cure is in the model: constrain and project few entities of an outline, in one skeleton sketch.
- **A revision that drops a constrained entity is refused whole**; the caller names the constraints to remove with it. Entries of the same sketch and later features are not protected: they break aloud at the recompute.
- **The weld moves an open end by up to the tolerance** (0.01 mm by default, and its slack of 1e-9 mm), onto one other end. It closes no chain: where three or more ends lie within the tolerance of each other without meeting, some stay open and are listed, and an end with more than eight other open ends within the tolerance is left alone (`crowded`). It does not change a file whose ends meet. A feature of an outline finer than the weld whose ends are open can be closed up by it; the report counts what moved and how far.
- **An open end of an arc beside a line that cannot come to it stays open** (the line's end is met by another curve already: three ends at one corner, which is no outline anyway). The report lists it; the weld does not move the arc.
- **Where two arcs meet with a gap, one becomes another circle**, through its new ends and its old middle. The arc of the file stays within the tolerance of it over its whole length. **Its radius has no bound once the sagitta of the arc is near the weld**: 0.8 % for a radius of 500 over 2° written with three decimals, 14 % for 100 over 1°, 22 % for 2000 over 0.2°, and a thousandfold for an arc pulled towards its chord (L9). Not bounded on purpose: a bound would leave open the joints whose radius the digits of the file do not decide. The report names each such arc with its radius before and after.
- **The centre of such an arc moves with its radius**, far for a shallow arc (by about the move of the end times the radius over the chord). The centre is an entity (`board/a3/center`) that a constraint, a pattern or a projection may name: what is built on the centre of an arc listed in `reshapedArcs` is built on a place the file does not hold. The same arc may also be reshaped otherwise in the next revision of the file. Cure: more digits in the export, or build on the ends of the arc.
- **Which of two arcs gives way** is the one whose radius changes less in proportion, compared in units of 1e-9; two arcs whose changes are that close are ordered by the file. A revision of the file that changes the proportions may reshape the other one.
- **Near the straight line an arc does not give way**: when the circle through its new ends and its old middle would have its middle within 1e-6 mm of the chord, or a radius over a million chords, the end stays open and is `blocked`. A larger weld does not close it; more digits in the file do.
- **A search that is cut short leaves ends alone.** More than 64 ends in the nine cells around an end (cells of the size of the weld: segments under about a tenth of the weld, or a hatch finer than it) make that end `crowded`, though it may have one clear partner (L5, its last row); and whether 64 is reached depends on where the cells fall, so in such a place a file may weld otherwise when it is moved. It errs to the side of changing nothing, and the report counts the ends. Cure: a smaller weld, or other layers. Not solved further: a search by distance in a place of any density is a spatial index of its own, beyond a prototype's reach in the last round.
- **A gap whose distance carries `atMost`** was measured among the first 64 ends around it: a nearer end may exist. The gaps of a dense place are an upper bound, not the list to choose a weld by.
- **Translation invariance holds to some kilometres.** The slack of the weld is 1e-9 mm; beyond about 4 km from the origin of the file the last bit of a coordinate is larger, and a gap exactly equal to the weld may again close at one place and not at another. The geometry itself holds further: a ring 500 km from its origin welds, is accepted and is a valid region (L2). Beyond 1000 km the engine refuses the coordinate (its range of ±1e9), with the message of a number out of range. Not solved: a drawing in the coordinates of a national grid in millimetres has to be moved to its origin before it is exported; the import does not do it, because the placement would then no longer be in the coordinates of the file, which a revision relies on.
- **A second weld over a welded outline changes nothing for files whose gaps come from rounding** (L1: none of 2200). It can for clusters at the scale of the join, where several ends lie between 1e-6 and a few 1e-6 mm of each other (93 of 3000 generated files, L3): after the first pass an end that was `blocked` may find its partner settled within reach. Not iterated to a fixed point: each pass would again move ends by up to the weld from where the pass before left them, which is the chain the bound forbids.
- **Splines that share both ends, the count of their points and the mean of their control points**, and are yet not twins, are compared with each other in the search for twins: quadratic in their number, which the limit of control points read (8000) keeps under 2700. No file of a drawing tool is like that.
- **Two arcs that meet need three decimals** to close with the default weld; where a line meets an arc two are enough.
- **An arc of nearly a whole turn read as a circle keeps the ID of an arc**, and is a circle in one revision and an arc in the next when its gap crosses the weld; what is constrained to it then holds the update back.
- **A tangency of two own curves that each start at another point of one corner** is not taken as one at a common end (a chain of two coincidents; D52).
- **Curves that cross in the file are not cut**: such an outline is an invalid profile, and `sketchContacts` lists the pairs. A curve that lies wholly on an earlier one is left out; one that lies on a part of another is not found. Cure: other layers, or the flag off and an own outline in a later sketch.
- **An outline is not cut in its own sketch.** A notch in an imported outline is own curves in a later sketch (6b's tool), or a second body cut from the first.
- **Cost, as measured on the files of the probes, not as a bound**: a change in a sketch that holds 2000 lines and circles that form regions is 100 ms; 500 splines of four control points 68 ms; 31 splines of 64 points 110 ms; with the flag off 5 to 17 ms. It follows the points of the profile, and several outlines in one sketch add up: the limits are per entry. The document grows by 70 characters a line and 190 a spline of four points, and so does every saved file; undo shares the entry, and a revision keeps the old curves in the undo stack.
- **The narrowing bounds nothing when constraints name most of an outline**: the solver gets what they name.
- **A region reference lists every curve of its outer loop**: an outline of 500 lines is 500 IDs in the extrusion that takes it, and its body has 500 side faces. As for any profile of that many curves. `get_sketch` prints such a loop short.
- **Not read**: ellipses and elliptical arcs, rational and periodic splines, splines above degree 3 and those given by fit points alone, blocks, text, hatches, 3D polylines, entities on a tilted plane; in SVG also CSS, `use`, nested `svg`, circles and arcs under an uneven transform, lengths in `%` or `em`. Each is listed in the report with a count, never silently.
- **A length with a unit in an SVG** is user units at 96 per inch, the rule of SVG: in a drawing whose `viewBox` makes a user unit a millimetre, `r="10mm"` is 37.8 mm. Drawing programs write such a file with bare numbers.
- **A hidden SVG element is read**, and a filled shape is its outline.
- **A DXF without `$INSUNITS` is millimetres**, an SVG without a size 96 units per inch; the report says so, and warns of bounds under 1 mm or over 10 m.
- **Broken path data on a layer that was not asked for is not seen**: the shapes of other layers are not parsed.
- **A segment between two vertices at one place** (of a polyline, of a path) is no curve and takes no ID; a degenerate curve written as an entity of its own takes one and leaves it unused.
- **The reader of DXF parses the groups of the whole text before it counts curves**: a file just under the limit of bytes is refused by its curves after 240 ms, not at once (I8).
- **`_outline` reads the file twice while a draft of the app is open** (once to answer whether the call changes the document, once to make the change), and each time previews or runs the command. Not memoised: the two steps would have to share a state across two functions of `tools.ts`, which holds none.
- **A refused placement is told by the app as a refusal, not as a failed call**: the outcome of the bridged call is `ok`, and anything that reads only the outcome (a log, a counter) sees a success.
- **The same outline in two sketches is stored twice** unless the second projects the first; and a projection does not carry a spline (6d), so an outline with splines that two sketches need whole is stored twice (the review, codex, on Open 1).
- **No placement that follows a body** except through parameters, and the cover of scenario 15 does not turn with its board (H6).
- **`get_sketch` and the query round positions** as everywhere; the exact numbers are in the document.

## Open

Nothing waits for the owner. Answered on 2026-11-25, each as recommended (answers 37 and 38 of [6-cross-review.md](../6-cross-review.md)): **the outline is stored in its entry** (no section, no schema step), and **`import_outline` sends the command itself** (and only reports when no sketch is named). The three rounds of review left no other question of the design to decide (what they left unsolved is in "Known limits"). The reviews agreed with both recommendations, each with conditions, which the revisions took in. The two questions as they were put:

1. **Where the outline is stored.** The plan says "stored in the document (like a stored mesh of D55)" and expects a section with a schema step. This design stores the curves in the entry that places them: one place, no step, `entityOf` from the sketch by construction, the update of the entry as the revision. *Recommendation: in the entry.* **Answered: in the entry (answer 37).** What a section would give, one outline placed in several sketches, a projection gives already, but for an outline with splines, which a projection does not carry (codex).
    - Checked by the review: the build before 6f refuses a document with an outline twice over, by the entry and by its stored value, so no step is needed and `SCHEMA_PENDING` stays 0; the object of the curves is shared by every document of the undo stack.
    - The reviewers' conditions, met: the options of the import are stored in the entry (`readWith`), and the validator copies what it is given.
    - A section can still come later: an entry could name one in the place of `curves`.
2. **What `import_outline` does.** The plan says it "answers with the batch". This design has it send the command (and only report without a sketch), because the batch would carry every curve to the caller and back, up to 140,000 characters each way. *Recommendation: it sends the command.* **Answered: it sends the command (answer 38).** `import_mesh` changes the document already (it stores the mesh), so this is the pattern that exists.
    - The reviewers' conditions, met: without a sketch it only reports; a refusal still answers with the report; a replacement names its entry, reads the file with the stored options, and has a way past the rule of an update in one batch (`remove`); the answer lists what a swap renamed; the same answer through the bridge and on the server's own engine, because one function runs where the engine is (the second round; a test the implementation owes); a call that only looks, or that is refused, does not end a draft of the app, and the file crosses the bridge as base64 (the third round).
